### 7. D1 first

One D1 database, every tenant row carrying an organisation id, gives simple reports and ordinary migrations. A Durable Object per organisation isolates more strongly but makes cross-team reports and migrations harder. Durable Objects join when a feature needs live coordination: a change that must be pushed to a person's other devices within a second.

Added on 2026-11-11 by TS-031, from Cloudflare's D1 limits page (<https://developers.cloudflare.com/d1/platform/limits/>):

- **The numbers.** A D1 database stops at 10 GB, and that limit cannot be raised. It runs one query at a time, so its throughput is one divided by the length of a query. A time entry is estimated at about 0.5 KB with its indexes, which is not yet measured; at that size 20 million entries fill the database.
- **The warning.** TS-022a adds an alert when the production database passes 5 GB.
- **The exit, named now.** Storage for each organisation: a database or a Durable Object of its own. `organisationScope` is the one module that would change, because every read and write of customer data already goes through it.
- **The rule.** Rows that arrive in high volume, such as audit records or imported calendar events, enter the shared database only with a period after which they are deleted.

### 8. Better Auth

Runs inside the Worker and keeps identities in our own D1 database. Supports email, passkeys, two-factor, organisations and roles. Cloudflare Access is built for a company's own workforce, not public sign-up. A hosted identity service would leave the Cloudflare stack. Hand-written authentication carries the most risk.

TS-008 confirmed the rest on 2026-11-11 against Better Auth's documentation for 1.7 and by running `better-auth` 1.7.19 and `@better-auth/passkey` 1.7.19, both pinned to that exact version. 1.7.20 was a day newer; it was published less than 24 hours before, which pnpm's release-age rule refuses, so the build uses 1.7.19 rather than make an exception to the rule. The tests pass on both.

**The route to D1.** The documentation gives two (<https://better-auth.com/docs/concepts/database>, "Example: Cloudflare D1"): hand the `DB` binding to Better Auth, which then uses its built-in Kysely adapter and creates its own tables through a migration endpoint; or use the Drizzle or Prisma adapter and migrate with that tool. We use the Drizzle adapter (<https://better-auth.com/docs/adapters/drizzle>) over the `drizzle-orm/d1` client the application already has.

| Option                               | Evidence                                                                                                                                                                                                                                                                                          |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Drizzle adapter, hand-written tables | One schema file and one migration tool for the whole database. The tables keep the house style: plural snake_case names, UUIDv7 ids (`advanced.database.generateId`), millisecond timestamps. Better Auth compares its models with the tables on start-up and every request waits for that check. |
| The `DB` binding, built-in adapter   | Fewer lines. Better Auth would create a second set of tables with its own names and id style, outside `migrations/`, through an endpoint that must then be protected or removed. `getMigrations` "does not work with Prisma or Drizzle", so the two routes cannot be mixed.                       |

What was run: every auth test drives the Worker's real fetch handler in the Workers runtime against a local D1 built from `migrations/`. `better-auth/minimal` is imported so the unused Kysely adapter stays out of the bundle, and each plugin from its own path (`better-auth/plugins/email-otp`), because the `better-auth/plugins` barrel loads every plugin.

**One instance per isolate.** The documentation builds the instance once at module scope from `env` imported from `cloudflare:workers`. Ours is built on first use and kept, which is the same thing with one difference: it is rebuilt if a binding it was built from is replaced, so a test can change the Turnstile key.

**Email code, not magic link.** The documentation describes both and recommends neither. A magic link is verified by a `GET` that signs the person in, and decision 18 says a `GET` never changes state. A six-digit code is typed into the page that asked for it, so it also works when the mail is read on another device. Codes are stored hashed, last five minutes and allow three attempts.

**Passkeys.** The plugin's default journey: prove the address with a code, then add a passkey while signed in. Every account therefore has a verified address to fall back on. The relying party id is the host of the request, which is only ever one of our own hosts.

**The `__Host-` cookie.** 1.7.19 and 1.7.20 have no option for it; the request is open upstream as <https://github.com/better-auth/better-auth/issues/10806>. What each configuration sent on 2026-11-11, read from the `Set-Cookie` header in a test:

| Configuration under `advanced`                                                             | Session cookie sent                                                                         |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Nothing                                                                                    | `better-auth.session_token`, with no `Secure` at all                                        |
| `useSecureCookies: true` and a cookie named `__Host-timesifier.session_token`              | `__Secure-__Host-timesifier.session_token`: the prefix is added in front of any name        |
| `useSecureCookies: false`, `cookiePrefix: "__Host-timesifier"`, and the attributes by hand | `__Host-timesifier.session_token=…; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax` |

The last row is what ships, and Better Auth reads that cookie back. The first row shows why nothing is left to the defaults: with the address taken from each request, Better Auth cannot know at start-up that it is served over HTTPS, and nothing sets production mode inside a Worker. With the prefix alone, the HTTP layer underneath Better Auth already adds `Secure` and `Path=/` to a name that starts with `__Host-`; the attributes are also set by hand so the cookie does not depend on that. Every cookie Better Auth sets takes the same prefix, including the passkey challenge. When upstream adds an option, moving to it will rename the cookie and sign everyone out once.

On `http://localhost` under `pnpm dev`, Chromium 158 kept the cookie and the next request had the session. WebKit (Safari 27.2) did not: sign-in answered 200 and the next request had no session. Firefox was not tried. Local sign-in and the browser tests therefore use Chromium.

**The rate limit.** Better Auth's own limiter with `storage: "database"`, so the count is one row in D1 shared by every isolate. It is off outside production mode unless `enabled: true` is set, so it is set. The client is the address in `CF-Connecting-IP`. Sending a code, signing in with a code and signing in with a passkey each allow 10 requests; the 11th is answered 429.

The window is neither a calendar minute nor a sliding count. The counter starts again only when 60 seconds have passed since the last request that was let through. Ten attempts 30 seconds apart are therefore followed by a 429, which is stricter than "ten a minute" for a slow, steady client. A refused request does not push the wait further out. `test/auth/rate-limit.test.ts` shows each of these.

Cloudflare's Rate Limiting binding was not used: its documentation says "Rate limits are approximate and apply separately in each Cloudflare location" (<https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/>), which cannot promise that the 11th request is refused.

**Turnstile.** The captcha plugin checks the token in the `x-captcha-response` header on the request that sends a code. With email codes there is no separate sign-up request, so that request is the door to sign-up; it is also the one that costs money and reaches a stranger's inbox.

Amended on 2026-11-11 by entry 22 and TS-027: a code has eight digits, not six, and one client may ask for a code three times a minute.

### 17. UUIDv7 ids and epoch-millisecond timestamps

Decided in TS-007, before the first table was created.

**Ids are UUID version 7 (RFC 9562), stored as 36-character lowercase text and generated in the application** by `uuidv7` in `app/db/`, with Web Crypto and no dependency.

| Option                 | Evidence                                                                                                                                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| UUIDv7 text            | The first 48 bits are the creation time, so ids sort by creation as plain strings and new rows land at the end of the primary-key index. Not guessable from a neighbour: 74 random bits. The id exists before the insert, so related rows can go in one batch. A published standard. |
| Auto-increment integer | Smallest and fastest. Reveals how many rows exist and lets a caller walk them, which matters for a multi-tenant product. The id is known only after the insert.                                                                                                                      |
| UUIDv4                 | Standard and unguessable. Random order scatters inserts across the index and says nothing about creation order.                                                                                                                                                                      |
| ULID, nanoid           | Would need a dependency or a format that is not a standard.                                                                                                                                                                                                                          |

Text, not a 16-byte blob: ids appear unchanged in URLs, logs and the D1 console, and Better Auth expects string ids. Ids created in the same millisecond are unique but not ordered among themselves. An id reveals when its row was created; none of our ids needs to hide that.

**Timestamps are integers holding milliseconds since the Unix epoch**, in columns `created_at` and, where rows change, `updated_at`, set by the application.

| Option                     | Evidence                                                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Integer epoch milliseconds | The epoch is defined in UTC, so a stored value cannot carry a time zone or be misread as local time. Compares and sorts as a number. It is what `Date.now()` returns and the precision the ids use. Eight bytes at most. |
| ISO 8601 text              | Readable in the console. SQLite has no date type, so nothing stops a value without a zone or in a second format, and comparison is correct only while every value has the same shape. Two to three times the size.       |
| Integer epoch seconds      | What SQLite's `unixepoch()` returns. Loses the order of events within a second, which a timer product needs.                                                                                                             |

Drizzle maps these columns to `Date` (`integer` with mode `timestamp_ms`), so code never handles the raw number.

### 18. Zod 4 for validation, and the origin-check rule

Decided while building TS-010.

**Validation.** Every action starts with `parseRequest` from `app/lib/validate.ts`, which checks the request's form data or JSON against a Zod 4 schema and answers 400 when it does not match.

| Option       | Evidence                                                                                                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Zod 4        | 4.6.7 on 2026-11-11, maintained by Colin McDonnell. No dependencies. One schema gives the check and the TypeScript type. Better Auth (decision 8) already uses it for its own schemas. |
| Valibot      | Smaller in the browser bundle. Validation here runs on the server, where that does not matter. A second schema library beside the one Better Auth brings.                              |
| Hand-written | No dependency. Every action would repeat type guards, and the types could drift from the checks.                                                                                       |

**Origin check.** The Worker answers 403 to a `POST`, `PUT`, `PATCH` or `DELETE` whose `Origin` header is present and differs from the request URL's origin, or whose `Sec-Fetch-Site` header is present and is neither `same-origin` nor `none`. A request with neither header is let through. `GET`, `HEAD` and `OPTIONS` are never blocked.

| Option                        | Evidence                                                                                                                                                                                            |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Header check in the Worker    | No state, no token in every form. Browsers send `Origin` on every state-changing request and a page cannot set it or `Sec-Fetch-Site`. Runs before the framework, so it covers resource routes too. |
| React Router's own check only | In 8.5.1 it answers 400 when `Origin` does not match, for page and data requests. Resource routes are not covered, and it does not read `Sec-Fetch-Site`.                                           |
| A token in every form         | Works without trusting headers. Needs a session before the first form, a hidden field in every form and a check in every action; one forgotten check is a hole.                                     |

A request with neither header does not come from a browser, and forgery needs a browser that holds the person's session. Session cookies are `SameSite=Lax` (TS-008) as a second layer. The consequence: a `GET` must never change state.

### 19. The Motion library is not added yet

Decided while building TS-005. It amends entry 10, which named the Motion library for springs and interruptible animation.

The components animate with CSS transitions that read the motion tokens, including the spring, which `pnpm tokens` emits as a CSS `linear()` easing. A CSS transition can be interrupted and reversed part-way, which is what design rule 8 asks for, and it runs under the Content Security Policy as shipped. Adding a library the platform can do without would break the dependency rule in `docs/security.md`.

Motion comes in with the first feature that needs what CSS cannot do: movement driven by a gesture, a spring that carries the velocity of an interrupted movement, or layout animation between two arrangements. The card that adds it says which. Route changes still use the View Transitions API, as entry 10 says.

### 20. The organisation comes from the request, not from the session

Decided while building TS-009.

Every request that acts on an organisation names it: a page by the slug in its address (`/app/<slug>/…`), a call to Better Auth by the organisation's id in its body or query. The server reads the person's membership of that organisation from the database on that request and answers 404 when there is none.

| Option                                   | Evidence                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The organisation is named by the request | What a request acts on can be read from the request alone, so a link, a second tab and a test all mean one thing. One check, in one place, covers every request. A person in two organisations can have both open at once.                                                                                                                                                                                             |
| The plugin's active organisation         | Better Auth's organization plugin keeps `activeOrganizationId` on the session and, in 1.7.19, its endpoints fall back to it when a request names no organisation. It is state the page does not show: two tabs share one session, so switching in one changes what the other's next request acts on, and an invitation or a removal can land in the wrong organisation. Reading it also ties tenancy to a mutable row. |

How it is held in place: the gate in `app/auth/organisations.server.ts` refuses, with 400, a request to an organisation endpoint that names no organisation, and answers 404 for the endpoint that sets the active organisation. The plugin still writes the column when a person creates or joins an organisation, because its schema requires the column to exist; nothing in the application reads it. `test/organisations/create.test.ts` proves a request without an organisation is refused even when the session has an active one.

### 22. A sign-in code is used in the browser that asked for it

Decided on card TS-027, after the security review of authentication.

The answer to a request for a code sets a cookie, `__Host-timesifier.sign_in_code`, whose value is an expiry and an HMAC under `BETTER_AUTH_SECRET` of the address and that expiry. A request to sign in with a code is refused, with the answer a wrong code gets and before the code's attempts are touched, unless it carries the cookie made for that address. The consequence a person can notice: a code read on a phone cannot be typed into a laptop that did not ask for it, and a code asked for in one browser does not work in another.

| Option                                      | Evidence                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A code works only in the browser that asked | A stranger's guesses never reach the code, so they cannot use up its three attempts. Before this, one client sending a wrong guess every six seconds stayed inside the rate limit and spent every code a person asked for within 18 seconds, for as long as it liked (the review's finding 2; `test/auth/email-code.test.ts`, "refuses a stranger's guesses", failed with 403 where it now gets 200). |
| A code works on any device (what was built) | Convenient: read the mail anywhere, type the code anywhere. But the sign-in request then has to accept a guess from anybody who knows the address, and Better Auth 1.7.19 counts attempts per address, not per requester (`plugins/email-otp/routes.mjs`, `atomicVerifyOTP`).                                                                                                                         |
| Turnstile on the sign-in request as well    | Raises the cost of each guess and does not stop the lock-out: three solved challenges still spend a code.                                                                                                                                                                                                                                                                                             |
| A separate code for each requester          | Would also stop one person's request replacing another's code. ### 25. Time entries: one running timer for a person in an organisation

Decided on 2026-11-11, before TS-011a starts. The owner settled the two questions that were open: a project is required, and who may see whose time.

- **The person's id stays.** `time_entries.user_id` does not cascade. Deleting an account removes the person's name and address and leaves the `users` row, so their entries still add up in the organisation's reports and show as "Deleted person" (TS-021a).

The columns and indexes of `projects` and `time_entries` are on cards TS-011a and TS-012a in `BOARD.md`, and move to `docs/architecture.md`, "Tables", when those cards are built.

### 26. Time zone: a name stored on the person

Decided by the owner on 2026-11-11, before TS-012a starts.

- **Where the zone comes from.** `users.time_zone` holds an IANA name such as `Europe/London`. It is set from the browser the first time the person opens a signed-in page, which for a new account is the page that follows the code, and the person can change it in Settings. A name is accepted only if it is `UTC` or `Intl.supportedValuesOf("timeZone")` holds it. Until one is stored, times are shown in UTC.
- **Which day an entry belongs to.** The whole entry belongs to the local day it starts in, in the zone of the person looking. An entry from 23:30 to 00:30 counts as one hour on the first day. That keeps "every total equals the sum of the entries shown" true without splitting an entry.
- **Nothing about a day is stored.** (Amended by entry 39: an entry's day is now stored.) Entries hold UTC instants (entry 17). - **Reports and exports.** Reports (TS-014a) and their export (TS-014b) follow the same rule. A report's range of days is bounded in the viewer's zone, `users.time_zone`; it holds the entries that start in that range, each counted whole on the day it starts, a running entry up to the time of the request. Every figure is whole minutes: an entry's length is floored to the minute once and totals add those minutes, so every total equals the sum of the rows shown (TS-091, W07). The CSV has one row for each entry the page lists, its times in UTC, in ISO 8601 with `Z`. The brief for the heading features (2026-11-11) had Reports bound their days in the organisation's zone and cut an entry at each of its midnights. TS-091 reversed that after the production audit of 2026-11-11 (W04, W33): the same entry counted on one day in the Timesheet and on two in Reports, so the two pages disagreed about one person's day, and the CSV listed one entry as two rows.

| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A name stored on the person (chosen)     | The server can render a page, and later a weekly summary, with no browser present. A person who travels keeps one answer to "which day was that" until they change it.       |
| The browser's zone on each request       | Nothing to store. The server cannot know the zone on the first request, and a job with no browser, such as the weekly summary, has no zone at all.                           |

### 27. A browser that has signed in before is counted apart, and its code is its own

Decided by the owner on 2026-11-11, on card TS-029, the same day as entry 23 and because of it. It narrows the gap entry 23 left open and amends entry 22: the cookie of entry 22 now names one request, not any request of the last five minutes.

The gap: somebody who knows a person's address could use up the five codes an hour the address may be sent, and could replace the code the person was about to type by asking for another. With no passkey there was no way in that did not need a code.

What was built. When a code signs a person in, the browser is given a cookie, `__Host-timesifier.known_browser`, kept for a year: an HMAC under `BETTER_AUTH_SECRET` of the lower-cased address, for each of the last five addresses signed in from that browser. From then on:

- **Two counts.** A request for a code from a browser that holds a proof for the address is counted against five an hour for such browsers. Every other request is counted against five an hour for everybody else. A stranger can use up only the second.
- **A waiting code is its asker's alone.** While the code of a known browser is waiting, a stranger's request is answered like any other and issues nothing, so it cannot replace that code. And a guess is let through to the plugin only from the browser whose request the live code answers, so a stranger who has asked, before or after, cannot use up its three attempts either.
- **One answer.** The status, the body and the cookie set by asking are the same in every case: served or not, known or not, account or none.

| Option                                               | Evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two counts and a waiting code of one's own (chosen)  | A person on a browser they have used before can always ask and sign in, whatever strangers do: `test/auth/known-browser.test.ts`, "can still ask for a code and sign in when strangers have used up the address's five in an hour", "is not replaced by a stranger's request" and "is not used up by a stranger's guesses". It costs a third cookie, one more row for each address with a code out, and an address may now be sent ten codes an hour and guessed at 30 times. |
| Accept the risk                                      | Nothing to build. Anybody who knows an address and will solve a Turnstile challenge every twelve minutes keeps its owner out for as long as they like, on every browser, and nothing but a passkey, which entry 23 removed, was ever going to end that.                                                                                                                                                                                                                       |
| A code for each requester, so that none replaces any | Would also protect a first sign-in on a new browser. The plugin keeps one live code for an address and compares a guess with the newest alone (`resolveOTP` and `atomicVerifyOTP` in `plugins/email-otp/routes.mjs`, 1.7.19); its `resendStrategy: "reuse"` sends the same code again and does nothing for a code stored as a hash, which ours is. It would mean writing the email-code flow ourselves. Not built.                                                            |

**What the plugin does with a pending code, and what was and was not prevented.** Every request creates a new code row for the address, and a guess is compared with the newest row only, so a request replaces the code before it. Prevented, by rules that run before the plugin and without changing it: a stranger replacing or using up the code a known browser is waiting for. Not prevented: a stranger's request replacing another stranger's code, which is what a first sign-in on a new browser asks for.

**Found on the way.** The cookie of entry 22 proved that a browser had asked for a code for the address within five minutes, and was set on every request, served or not. Anybody who asked could therefore still spend the three attempts of a code sent in answer to somebody else's request: in `test/auth/email-code.test.ts`, "refuses the cookie of a browser that asked for an earlier code", the earlier browser's fourth wrong guess was answered 403, the code used up, where it is now answered 400 and the code still signs in the browser that asked for it. The cookie now carries a number of its request's own, and the server keeps the number of the request the live code answers.

**What stays open** is in `docs/security.md`, "Known gaps", rows TS-029:

- A first sign-in on a new browser, sign-up included, can still be delayed: its request is a stranger's, so the strangers' five can be used up before it, and a stranger's later request replaces its code.
- A proof cannot be withdrawn and signing out does not remove it. Whoever holds a browser that once signed in as an address can do to the known browsers' count what a stranger could do to the one count before.
- While a known browser's code waits, for five minutes at most, the same person asking from a new browser is sent nothing and is not told.

Signing out everywhere does not clear the proof: it signs nobody in, the person who has signed out is the one who needs it next, and a request from one browser cannot reach a cookie in another.

### 34. Placement and caching: the Worker runs near the database; the built files are kept

Decided on 2026-11-12, on card TS-096, after the owner saw the Timesheet blink on a reload.

**Placement.** The Worker runs near the database, not near the visitor: `"placement": { "region": "aws:eu-central-1" }` in `wrangler.jsonc`, a Placement Hint ([Cloudflare, Placement](https://developers.cloudflare.com/workers/configuration/placement/): "Placement Hints run your Worker in the data center with the lowest latency to your specified cloud region"). `aws:eu-central-1` is Frankfurt. The database is D1 in the `eu` jurisdiction and runs in Eastern Europe (`wrangler d1 info`: `"running_in_region": "EEUR"`, read replication disabled; the preview database the same). A page asks D1 several questions in turn, and each was a round trip from the data centre that took the request: for this machine Newark (EWR), across the Atlantic. `/app/<slug>` took 2.1 to 2.6 seconds to its first byte (curl) and the owner's signed-in tab 1305ms, with the old page on screen all that time. A request still reaches the data centre nearest the visitor first, which passes it on, and "Static assets are always served from the location nearest to the incoming request" (the same page). Previews inherit the setting.

**Caching.** Every file under `/assets/` has a hash of its content in its name, so `public/_headers` gives them `Cache-Control: public, max-age=31536000, immutable`. Before, a reload of production revalidated each one (62 requests answered 304) and the stylesheet's extra round trip held back the first paint. Pages and their `.data` answers stay `private, no-store`.

| Option                                  | Evidence                                                                                                                                                                                                                                                               |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A Placement Hint for Frankfurt (chosen) | In force from the deploy, with no traffic to learn from. One back end in one known region is the case the documentation gives for a hint.                                                                                                                              |
| Smart Placement                         | Decides from traffic "from multiple locations", "may take up to 15 minutes", and "only considers locations where the Worker has previously run"; with little traffic it can stay `INSUFFICIENT_INVOCATIONS`, and 1% of requests are left where they are as a baseline. |
| D1 read replicas                        | Copies for reading elsewhere, but a database in the `eu` jurisdiction keeps every copy inside it, so none comes nearer a visitor outside Europe; every query would also have to go through a session that carries a bookmark to read its own writes.                   |
| No placement                            | Each of a page's questions crosses from the visitor's data centre to Eastern Europe and back.                                                                                                                                                                          |

**What it costs.** A request makes one extra journey, from the visitor's data centre to Frankfurt, before the first question is asked: about 115ms from Newark, paid back once a page asks two questions. A visitor near Europe gains little. The public pages said a request was handled by the data centre nearest the visitor; they now say it is passed to Frankfurt, and `test/claims.test.ts` fails if that sentence and `wrangler.jsonc` part. Placement "only affects the execution of fetch event handlers": the scheduled work in `workers/scheduled.ts` runs where Cloudflare starts it. "At extremely high request volumes (hundreds of thousands of requests per second or more), Cloudflare may run instances across a more distributed area." The `cf-placement` header, which says where a request ran, "may be removed before Smart Placement exits beta"; `scripts/placement-ttfb.sh` then reports `none` with nothing changed.

On one kept-alive connection, 24 requests each, the median time from sending a request to its first byte: a static file (no Worker) 107ms on the preview and 110ms on production, so the network is the same; `/robots.txt` (the Worker, no query) 219ms against 104ms, the journey to Frankfurt; `/api/v1/me` with an unknown token (the Worker and one D1 query) 261ms against 234ms. One query therefore cost 42ms from Frankfurt and 130ms from Newark: a page that asks ten questions in turn saves about three quarters of a second.

**Measured in production on 2026-11-13, after #57's deploy (13:42 UTC), from this machine (EWR).** Every request `cf-placement: remote-FRA` (`scripts/placement-ttfb.sh https://timesifier.com 15`). On one kept-alive connection, 24 requests each, the median time from sending a request to its first byte: a static file 110ms, `/robots.txt` 241ms, `/api/v1/me` 254ms; the same morning, before the deploy, 107ms, 117ms and 235ms. The network is unchanged; the journey to Frankfurt adds about 125ms (the preview's 115ms); one D1 query costs 254 − 241 = 13ms from Frankfurt against 235 − 117 = 118ms from Newark before. ### 39. An entry's day is stored when it is tracked

Decided by the owner on 2026-11-13 (TS-111), amending entry 26, after the time-rules review (`research/time-rules-scenarios.md`, TR-03, TR-05 and TR-06).

Entry 26 stored no day: every reader worked out an entry's day from its start in the zone of whoever was looking, as that zone was then. Three bugs came of it. A person who changed their own zone moved entries across the lock date and out of approved weeks, where they could be changed and deleted again (TR-03). Reports bounded another person's days in the reader's zone, so an owner in London read 34:00 of a week that a person in Auckland submitted and had approved as 37:30 (TR-05). A timer stopped after midnight and cut at the day's limit put its overtime on the next day, a day of leave or a holiday among them (TR-06).

- **The day.** `time_entries.spent_on`, a local date `YYYY-MM-DD`, is written once by every writer: the timer from the day it starts on in the person's zone, hours tracked and typed cells from the day chosen, an edit from the day typed when the start moves, the API from `spent_date`, the CSV import from the row's date. A timer cut at the limit keeps both parts on the day it started. Nothing works it out again on reading.
- **Every reader reads it.** The Timesheet, day limits, overtime and its caps, submission, locks and auto-submit, Team and Approvals, Reports and their CSV, Dashboards and utilisation, the project page, budgets, contractors, invoices from time, calendar feeds, History and both exports bound and group entries by `spent_on`. Each person's days are therefore their own wherever they are read, and a report of a week holds the week its person submitted. A change of zone changes how clock times are shown and where new time lands, and moves nothing tracked.
- **The backfill.** Migration `0023_entry_day_backfill` gave every entry tracked before it the day it showed then: the day its start falls on in its person's zone today, else the organisation's. Nobody saw a day move. SQLite knows no zones, so `scripts/entry-day-backfill.ts` writes each zone's UTC offsets from 2000 to 2040 into the SQL, one statement per group of zones with the same offsets; a zone it does not know is read as UTC. Two triggers then refuse a row whose day is not a real date, and two indexes, `(organisation_id, spent_on)` and `(organisation_id, user_id, spent_on)`, serve the readers. `test/db/entry-day-backfill.test.ts` compares every day it writes with `dayOf`.

| Option                                    | Evidence                                                                                                                |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Store the day when it is tracked (chosen) | Settles TR-03, TR-05 and TR-06 with one column. It is Harvest's shape (`spent_date`), which the API already spoke.      |
| Keep entry 26 and refuse a change of zone | Settles TR-03 only while the refusal holds, and a traveller could not correct their zone; TR-05 and TR-06 stay.         |
| Store the zone on each entry              | The day can be worked out again, but every reader still converts instants to days, and SQL still cannot bound by a day. |
| Bound Reports in each person's zone       | Settles TR-05 at the cost of a range per person in every report query; TR-03 and TR-06 stay.                            |

**What it costs.** Ten bytes and two indexes an entry. The backfill migration is about 214 KB of SQL, 192 statements, run once. An entry no longer moves when its person's zone changes, which is the point, but a person who tracked a week in the wrong zone and then corrects it sees those entries stay on the days they were tracked on; an edit moves one. The rule of entry 26 for an entry's whole length on its first day stands. A writer that forgets the day is refused by the database, not corrected.

### 40. A list goes to D1 as one JSON value

Decided on 2026-11-13 (TS-112), on the measurement in `research/corporate/scale-test.md`.

D1 takes at most 100 bound parameters a statement ([Cloudflare D1 limits](https://developers.cloudflare.com/d1/platform/limits/): "Maximum bound parameters per query: 100", applying to each statement of a batch too). Drizzle's `inArray(column, ids)` binds one parameter a value, so every list that grows with an organisation's people, projects or records failed once it held about a hundred: every page an owner or admin opened answered 500 in an organisation of about 99 members, through the Approvals link the shared layout counts; Activity and `/time_entries` failed in any busy organisation.

A list now goes to D1 as one parameter: `among(column, ids)` in `app/db/among.ts` writes `column in (select value from json_each(?))` and binds the list as one JSON array, each value once; `notAmong` is its opposite. SQLite still uses the column's index (`LIST SUBQUERY … SCAN json_each`). `inArray` stays only over a fixed list of constants (`["pending", "approved"]`, `[...OWING, "paid"]`), and `test/node/lists.test.ts` fails `pnpm test` on any other `inArray(` or `in (${…})` written into SQL in `app/`, naming its file and line. A count that needs no list does not read one: the Approvals link is one `count(*)` (`app/db/waiting.ts`).

| Option                                    | Evidence                                                                                                                                                                                                                                              |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One JSON parameter, `json_each` (chosen)  | One parameter however long the list; one statement, so one round trip; the index is used. The list is a bound value, so it counts against D1's 2 MB a string (about 50,000 ids), not its 100 KB a statement. Five modules had already written a copy. |
| Chunks of 90 ids, a statement each        | Works, at a round trip a chunk, and every caller must remember to chunk and merge; three places instead cut the list at 90 and silently left out the rest.                                                                                            |
| A join or subquery in place of each list  | Best where the list is itself a query (the Approvals count), but most lists are ids a page has already read from another table, or from D1 and then filtered by a rule written in TypeScript.                                                         |
| A temporary table filled before the query | Several statements a read, and D1 offers no session-scoped temporary tables across a batch.                                                                                                                                                           |

**What it costs.** A list is serialised to JSON on every call, which is cheap beside the round trip it saves. A list longer than D1's 2 MB a string, about 50,000 ids, would fail; none is that long, since the longest lists are an organisation's people and a page holds at most 500 records. Read the same day from <https://developers.cloudflare.com/d1/platform/limits/>, last updated 2026-10-30.

**Better Auth's own limits (TS-112).** The organization plugin holds an organisation to 100 members (`membershipLimit`) and 100 pending invitations (`invitationLimit`) unless told otherwise, and every list the library reads stops at 100 rows (`advanced.database.defaultFindManyLimit`), its invitations among them. All three are `LIBRARY_CEILING`, 1,000,000, in `app/auth/organisations.server.ts`: how many people an organisation holds is decided by the seats on its plan, checked before an invitation is made, and no plan holds that many (`MAX_SEATS` is 10,000). Teams are not enabled, and their limits are unset, which the plugin reads as none. `GET /organization/get-full-organization` and `GET /organization/list-members` are withdrawn from `app/auth/endpoints.ts`: no page called them, and the plugin reads their members' people with `inArray`, a bound parameter each, so they answered 500 past about 99 members whatever the limit. The Members page reads D1 itself (`membersByJoining`). The organisation endpoints still offered read no list of members in one statement; `test/lists/membership.test.ts` calls each in an organisation of 150 and expects 200, and fails until a newly offered endpoint has a request there.

### 57. A report is added up in SQL; its money is priced once per span of days in which no rate starts

Decided on 2026-11-23 (TS-113), on D4 of the scale test (`research/corporate/scale-test.md`), with the after measurement in its "After TS-113" section.

Reports, Utilisation, Profitability, Dashboards and the project page's profit read a report's entries 200 at a time, one query after another, and added them up in the Worker (`entryPages`, `rowsOfReport`). For the owner of an organisation of 300 people a month was 217 statements and 21,167 rows, and a year 2,147 statements, 215,307 rows and 35 s locally: past D1's 1,000 queries an invocation on Workers Paid, so it failed in production.

- **One statement.** `sumsOf` (`app/reports/sums.server.ts`) adds a report up in one statement through the organisation's scope, grouped by person, project, whether billable and whether overtime: what the Time view, Utilisation and Dashboards show. Each entry counts its whole minutes on its stored day (decision 39), a running one up to the time of the request, exactly as `rowOf` counts it one by one, so every figure is the sum of its entries. Days and timetables are further groupings of the same statement (`byDay`). The Time view lists its first 200 entries in the order of decision 58 and counts the rest in the sums.
- **Money, once per span.** A rate (billable or cost) starts on a day and holds until the next starts (`app/rates/price.ts`). When money is priced, the groups are also kept apart by task on a project billed by task, and by span of days in which none of the organisation's rates starts: `latestAmong(spent_on, starts)` (`app/db/among.ts`) names each entry's span by the latest rate start on or before its day, in one bound parameter. Every entry of a group is then priced at the same rate, so pricing the group's minutes once (`priceTime`) is pricing each entry and adding them up. How many groups there are is bounded by people × projects × tasks (on projects billed by task) × (rate starts in the range + 1), whatever the number of entries. Budgets (`projectBudgets`) and Contractors group the same way.
- **Regular and overtime apart.** Every money sum keeps regular and overtime minutes in groups of their own: in the reports' sums, the budgets, Contractors and Team's week, each group carries its `overtime` flag. TS-111f's overtime multiplier (`projects.overtime_rate_milli`, #81) is then one factor on the overtime groups' price where they are priced: `billableSplitOf` (`app/reports/amounts.server.ts`), `profitability` (`app/reports/profitability.ts`), the fee budgets (`app/budgets/budget.server.ts`) and `contractorLines` (`app/contractors/contractors.ts`).
- **The figures did not move.** Before the change, `test/reports/sums.test.ts` pinned the Time view, Utilisation, Profitability and Dashboards for each role over a company with overtime, half days of leave, missing rates and entries either side of midnight in three zones, and `test/budgets/spend.test.ts` pinned every kind of budget; the code that read every entry wrote both. Their snapshots held record ids, which are partly random (uuidv7), so even that code failed them on a second run. They now name each record instead (`stable` and `namesOf` in `test/reports/company.ts`). The code from before TS-113 (`d05bd38`) rewrote both snapshots, and every figure in them is the committed one; only the ids, and the order of the entry list (decision 58), differ. The new code passes them unchanged.

| Option                                                  | Evidence                                                                                                                                                                                                                  |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One summed statement, priced per span of rates (chosen) | Statements no longer grow with entries: a year is a handful, and the rows read are the groups, not the entries. Exact, because a group never straddles a rate start. Keeps overtime apart for TS-111f.                    |
| Keep reading every entry, in larger pages               | Fewer rounds, but the rows read and the Worker's memory still grow with the entries: a year of 300 people is 211,000 rows, and D1's 1,000 queries a request is only pushed further away.                                  |
| Price each entry in SQL, joining its rate               | One statement too, but SQL would have to repeat `priceTime`'s rounding, rate modes and currencies, and two copies of the money rules would drift.                                                                         |
| Group by day, then price each day                       | Exact and simple, but the groups grow with days × people × projects: a year of 300 people is tens of thousands of rows again.                                                                                             |
| Running totals in a table updated with each write       | The cheapest read, but every writer (timer, cells, API, import, undo, locks) must update it in the same batch, and a report's people, tags and days are chosen when it is read, so the totals would still need adding up. |

**What it costs.** A report's groups are numbers, not entries, so its page no longer holds every row: a group's people and the People section beyond 50 are read when they are opened (decision 58). The number of groups grows with the rate starts in the range; an organisation that changed rates every day would make many groups, still far fewer than its entries. The CSV export still writes every entry, in keyset pages (decision 58).

Holding them to the policy would break every integration the day the policy is turned on, and neither carries a sign-in method to hold. An owner who wants them stopped revokes them.
- **The verification token is plain text.** The value it proves goes into a public DNS record, so hashing the stored copy would protect nothing; the owner must be shown it again on any visit to copy it. It is 128 random bits per organisation and domain, so a record published for one organisation proves nothing for another.
- **Uniqueness covers verified claims only.** A partial unique index on `organisation_domains.domain` where `verified_at` is set. Any organisation may write a domain down, so a squatter that adds a domain first blocks nobody: the one that proves it, verifies it; a second proof is refused while the first holds. Unverified after 14 days without its record, a domain is free for the next organisation that proves it.
- **DNS over HTTPS instead of `node:dns`.** `resolveTxt` under `nodejs_compat` is itself a DNS-over-HTTPS client to Cloudflare's resolver, so a `fetch` to `cloudflare-dns.com/dns-query` with `application/dns-json` (`app/organisations/dns.server.ts`) does the same with no compatibility layer, and a test stubs it like any other `fetch`. A lookup the resolver cannot answer counts as the record not seen (below).
- **Re-checks.** The daily job looks every domain up again. A verified domain whose record has been missing for 7 days gets one email to its owners, once each time it goes missing; after 14 days it is unverified, so a lapse of a few days in a DNS migration costs nothing. A failed lookup counts toward both, as a record not seen (security review of #89, LOW b): otherwise a resolver that fails, or is made to fail, for a fortnight would keep a domain verified that its record has left.
- **Joining needs fresh proof of the address** (security review, MEDIUM). `email_verified` says the address was proved once, perhaps years ago at a mailbox since closed or given to someone else. So joining by a domain also asks the session to prove it now (`provesAddress`): a code emailed to the address and used within the last 15 minutes; Google, from a Workspace account whose `hd` is the address's domain; or Microsoft, whose sessions are made only for an address it vouches for (`xms_edov` or `email_verified`), from a work tenant that issued the token itself. Anyone else is told to sign in again with a code.
- **A person removed waits for an invitation** (security review, MEDIUM). `membership_removals` (migration 0031) keeps who removed whom and when, written after every `/organization/remove-member` whichever page asked. Until the organisation invites them after the removal, the person is not offered the join and is refused if they ask; otherwise an owner's removal would last only until the person pressed "Join".
- **The seat is taken in the insert** (security review, LOW a). The membership is written only while the organisation's members and pending invitations are fewer than its seats as that statement runs, and its activity record only when the membership was, in one batch. Two people joining at once for the last seat cannot both have it; the second is told the organisation is full.
- **A domain is joined by only while its record is fresh** (security review, LOW b): found by a lookup in the last 48 hours. A domain whose record has gone keeps its verification for 14 days, for the owners to put it back; it does not keep letting strangers in for those 14 days.
- **A policy the code cannot read is locked** (security review, defence in depth). A row whose provider this code does not know, or whose policy word is neither `any` nor `company`, is met by no session: only the owners open the organisation until one of them chooses again. Reading it as open would let in everybody it was meant to keep out.
- **A tenant is advised, not required** (security review, LOW d). Without a Workspace domain or a tenant ID, any Google account, or a work account at any Microsoft tenant, meets the policy. Settings › Sign-in says so beside the policy and the field; saving is not blocked, because "only Microsoft accounts" is a policy some organisations want.
- **One way to a membership** (security review, LOW c). The organisation layout's `requireMembershipOf` is the only exported way to read a membership; the function that reads it without the policy is private, so no new page or loader can skip the policy by reaching for it.
- **Every plan** has it (answer 8, option a). SAML or OIDC per organisation is 104d, on Business, built when a customer asks.

**The limit.** Cloudflare's D1 limits page gives, for "Queries per Worker invocation", "1000 (Workers Paid) / 50 (Free)", and says a `db.batch()` call counts as a single query against it (<https://developers.cloudflare.com/d1/platform/limits/>, modified 2026-11-20, read 2026-11-24). A run starts an item, an organisation's own reminders or one running timer, only while 30 queries are left for it (`ITEM_QUERIES`); one query is kept back for writing where it stopped. Measured on 2026-11-24 in the Workers test runtime, by the queries a run reports: 1 for a minute whose hour's pass is finished; 5 for a run that starts a pass with nothing to remind; about 22 for an organisation's own reminders, its deadline due and weeks waiting, whatever its size; 4 to read an organisation's running timers; about 10 for each timer. When the share is spent the run stops cleanly: what it made is written, and where it stopped (`test/notifications/reminders-pass.test.ts`, "a run's share of the invocation's queries": six timers with a share of 60, each run within it, each person reminded once).

**Every minute, from where the last stopped.** A pass checks every organisation with work once, in the order of their ids, each organisation's own reminders and then its running timers in the order of theirs. Where it stands is one row, `reminder_pass` (migration `0037_reminder_pass`): the hour it started, the last organisation and timer checked, and when it finished. The hourly run starts the hour's pass after auto-lock, the lock date and billing, so the reminders read the weeks and timers those left; every other minute's run goes on with it, and in the hour's first minute the every-minute run leaves the reminders to the hourly one. A pass starts once the one before is finished and the hour is a new one; a pass that has not finished goes on into the next hour rather than starting again, so no organisation late in the order is left out. Chosen over keeping the reminders hourly: a share of 400 an hour reaches about 38 timers, and what it did not reach would wait an hour for each 400 queries more, never catching up while timers keep running. Sixty runs an hour reach about 23,000 queries: about 2,000 timers, or about 1,000 organisations with work, in the hour; one organisation of 300 people with 65 timers takes two minutes. More than that and a pass runs past its hour, and the reminders it has not reached go later, still once each and in their period.

**The lease.** A run takes the pass in one statement, `takeReminderPass`, with a token of its own, for `REMINDER_LEASE_MS`, two minutes, and only when no run holds it or the lease of the one that did has run out; with the hour's pass finished it takes nothing, the minute's one query. It starts no item after half its lease, so it lets the pass go well before the lease runs out, and lets it go with one statement that writes where it stopped only while its token still holds the pass. So a run that dies holding the pass holds it two minutes at most, and the next run takes it over and goes on from the last place written; two runs at once never both check the same item, and one that has lost its lease writes nothing (`test/notifications/reminders-pass.test.ts`, "the pass's lease"). An organisation whose item fails is logged by its id and passed over; the rest of the pass goes on.

**Each duty on its own.** In every cron, each duty runs in its own `try`: one that fails is logged by its name and the next still runs, in their order, auto-lock, the lock date and billing before the reminders (`runEach` in `workers/scheduled.ts`; `test/scheduled/duties.test.ts`).

**What remains: TS-049b.** The reminders' share is now bounded, and none is lost when there is too much for one run; but every organisation shares one pass, so at about 1,000 organisations with work an hour a reminder can come an hour late. ### 70. Team's week is a capacity table: each person measured against their expected week, ordered by the figures across every page

Decided for TS-125 (research/harvest-sweep-2.md, S2-08).

**What a row says.** Each person on This week has their time logged, overtime apart as before ("37:30 + 2:00 overtime"), the time expected of them, and their leave, then a bar and a line in words: "3:45 under · 89% of capacity", "2:00 over · 105% of capacity", "On capacity" within a minute either way, and "1:00 over, nothing expected" for time on a week that expected none. The expected time is the one Reports and the person's own week already use: their schedule's week less public holidays and approved leave (`leaveOfPeople`, `expectedMinutes`), so the three pages cannot disagree. The share is never shown without the hours beside it.

**The bar.** Primary for the time logged up to what was expected, error past it, and the week's approved leave as a hatched stretch after the expected time, so leave visibly shortens the week by its hours. Over and under are said in words beside it and read out by the bar's `aria-valuetext`; colour is never the only sign. Drawn in SVG lengths, so no `style` attribute is written (docs/security.md), as the budget bar is.

**The headline.** The week's logged total of everyone the search keeps leads the page in the Reports style, "103:30 of 198:45 expected", and is the sum of the rows on every page. The total at the sheet's foot stays, with the expected and the standing under it.

**The order.** Name (the default, left out of the address), Most logged, Most of capacity and Most remaining, in `?sort=`. The Week's arrows, the pages and the search keep it. People who tie keep the order by name. Time logged where none was expected sorts above every share. The people the viewer pinned still come first, each part in the order chosen.

**Paging and the figures.** To order by the figures across 50-a-page lists, every person the search keeps is measured before a page is taken: what they logged is one `SUM … GROUP BY user_id` statement (`loggedByPerson`), which also gives the page's rows and the total, so no entry is read row by row; what they were expected is one reading of the schedules, leave and holidays for all of them. The page's 50 alone go to the browser. Team's statements for a manager of 120 went from 36 to 35.

| Option                                                | Evidence                                                                                                                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Measure everyone the search keeps, then page (chosen) | An order that holds across pages; one sum and one leave reading whatever the count, the statements the same for any order or page (`test/pages/capacity.test.ts`).             |
| Order only the page's 50                              | Fewer people measured, but "Most remaining" would mean the most remaining among A to Ax: page 2 could hold someone further under than page 1.                                  |
| Order in SQL, with expected hours as a column         | Would page in the database, but expected hours come from dated schedules, leave halves and holidays in the people's own zones; repeating that in SQL would be a second reader. |
| Colour the over and under rows                        | Harvest's look, but a colour alone says nothing to a screen reader or in some schemes; the words carry it and the bar repeats it.                                              |

**Left out.** The sweep's filter by team and the running timer's project in the row: neither is part of this card. Billable time in the headline stays in Reports.

**What it costs.** A search that keeps thousands of people reads the leave and schedules of all of them on each page, where it read 50; the statements are the same in number. The bar is one more SVG per row.
