# Design system

Material 3 Expressive is the design language. Benji Taylor's three principles decide how the product behaves. We build our own components on React Aria Components and style them only with tokens.

Why this and not a ready-made Material library is in `docs/decisions.md`, entries 4 to 6.

## Principles

From _Family Values_ (benji.org/family-values): "Simplicity ensures accessibility, fluidity maintains continuity of experience, and delight fosters meaningful connections."

| Principle  | What it means here                                                                      |
| ---------- | --------------------------------------------------------------------------------------- |
| Simplicity | The fundamentals are at hand. Everything else appears when it becomes relevant.         |
| Fluidity   | Every change of view is a movement the person can follow. "We fly instead of teleport." |
| Delight    | Selective emphasis: the same polish everywhere, with special moments placed on purpose. |

## Rules

Each rule can be checked in review or by a test.

### Simplicity

1. A view or sheet has one primary action.
2. A task that is brief or belongs to the current view opens in a sheet over that view: confirming, quick editing, warnings. A new page is for work that stands on its own.
3. A sheet holds one piece of content or one action. A sequence of sheets shows a title and a back control.
4. Settings a person rarely needs sit behind a clearly named control, never on the main view.

### Fluidity

5. Route changes animate in the direction of travel: forward and to the right move one way, back and to the left the other.
6. An element that is on screen before and after a change stays the same element. It moves; it is never removed and redrawn.
7. A label or number that changes animates the change: timer digits, totals, a button going from "Continue" to "Confirm".
8. Every animation can be interrupted by the next input.
9. With reduced motion requested, movement and scaling are replaced by a fade or nothing.

### Delight

10. Every screen gets the same polish, including the ones used rarely: settings, empty states, errors.
11. The strongest moments go to events that are significant and rare: creating an account, the first tracked hour, closing a week.
12. Actions repeated many times a day, such as starting and stopping a timer, get subtle feedback that never delays the next action.

### Material and accessibility

13. Components read colour, type, shape, spacing, elevation and motion from tokens. Raw colours and sizes fail `pnpm check:tokens`.
14. Light and dark schemes come from one seed colour. Text meets 4.5:1 contrast in both.
15. Everything works by keyboard, with a visible focus indicator.
16. Pages meet WCAG 2.2 AA; automated checks run in the pipeline and a manual keyboard pass is part of TS-023.
17. Layout follows Material's window sizes: a navigation bar when the window is under 600px wide, a navigation rail from 600px.

### Colour schemes

`:root` declares `color-scheme: light dark`, so each role follows the device setting. `data-color-scheme="light"` or `data-color-scheme="dark"` forces one scheme: on the `html` element for the whole page, or on any element for that part of it. Because every role already carries both values, components need no `dark:` variants. An element that forces a scheme must also set its own background and text colour (`bg-surface text-on-surface`), since those are inherited as colours already worked out.

### The spring

The spring is defined once, by its stiffness and damping ratio. `pnpm tokens` derives two forms from those numbers:

- `--md-sys-motion-spring-stiffness` and `--md-sys-motion-spring-damping`, the values the Motion library takes (mass 1);
- `--md-sys-motion-spring-easing`, a CSS `linear()` curve sampled from the same spring, with `--md-sys-motion-spring-duration`, the time it takes to settle within 0.1% of its target.

### Changing a token

To change the seed colour, edit the one `SEED_COLOUR` line in `scripts/tokens.ts`, run `pnpm tokens`, then `pnpm test`, and commit the script and `app/styles/tokens.css` together. The contrast test checks every text role against its background in both schemes; if a pair falls below 4.5:1, raise the scheme's contrast level in `scripts/tokens.ts` and leave the test alone. The type scale, corner scale, spacing unit, elevation, durations, easings and the spring change the same way. To change the typeface, install its Fontsource package and edit `TYPEFACE`.

### What `pnpm check:tokens` rejects

Under `app/`, outside the generated `app/styles/tokens.css`:

- a hex colour, such as `#fff` or `#4f5bd5`;
- a utility with a bracketed value, such as `w-[13px]`, `bg-[#fff]`, `text-[color:red]`, `bg-primary/[0.5]` or `min-[320px]:`;
- a bracketed declaration used as a class, such as `[mask-type:luminance]`.

Bracketed variants that only select a state, such as `data-[state=open]:`, are allowed. The check reads text, not syntax: it also reports a hex colour in a comment, and three or four hex digits after a bare `#` (write "issue 123", not `#123`).

The specification column names the token files read on 11 Nov 2026 in Material's published token set, `tokens/versions/latest/sass/_<name>.scss` in github.com/material-components/material-web ("Google Material 3, Version 34.0.21"). Widths, paddings and the 48px touch target that the token files leave out come from the Compose Material 3 sources (github.com/androidx/androidx, `compose/material3`). m3.material.io renders its specification pages with script, so no value was taken from it.

Where a component departs from those files:

- **Checkbox corner is 4px.** Material draws 2px; the corner scale's smallest step is 4px, and a component does not carry a size of its own.
- **A hovered field darkens its label** to `on-surface` (`on-error-container` when invalid). Material keeps `on-surface-variant`, which measures 4.33:1 on the hover layer in the light scheme, under the 4.5:1 that rule 14 requires.
- **The sheet has no drag handle**, because it is not dragged. It closes by Escape, by pressing outside, or by its own buttons.
- **A snackbar's text is a `status`, not an `alert`**, so it is announced when the screen reader is next idle. React Aria's toast defaults to `alert`.

### How the components move

- **Overlays enter and leave with movement.** A menu and a select's list grow out of their button; a dialog rises and grows; a sheet slides up from the bottom edge; a snackbar rises; a tooltip grows. The spring (`ease-spring duration-spring`) carries what arrives; leaving is short and accelerates away.
- **A change of selection moves the thing that marks it.** The tab indicator slides to the selected tab, the switch handle travels along its track, and a field's label floats up when the field takes focus.
- **Everything is a CSS transition that reads the motion tokens**, so the next input turns a movement around from where it is (rule 8) and nothing waits for an animation to end (rule 12). The Motion library is not installed yet: none of these components needs what a transition cannot do. It joins with the first component that does, such as a gesture.
- **With reduced motion requested, only opacity and colour change.** Classes that move or scale sit under `motion-safe:`, and each moving element has a `motion-reduce:` class that narrows what it transitions. `e2e/reduced-motion.spec.ts` operates every component and fails if anything animates position or size.

### The gallery

`app/routes/design.tsx` is the `/design` route. It is registered by `app/routes.ts` only under `pnpm dev`, and in a build made with `DESIGN_ROUTE=1`, which is the build `pnpm test:e2e` makes and then deletes. A normal `pnpm build` leaves it out: production answers 404 (`test/design-route.test.ts`).

- Each half sets `data-color-scheme`, and overlays opened from a half render inside it, so they take its scheme.
- Hover, focus and pressed are held in place by setting the attributes React Aria sets for them.
- An overlay opens from its button. `/design?open=dialog&scheme=dark` opens one as the page loads; `open` is `select`, `menu`, `dialog`, `sheet`, `tooltip` or `snackbar`.

### Adding a component

1. Read Material's token file for it and note the values: sizes, shape, colour roles for each state.
2. Render the React Aria component you mean to build on with `renderToString` and look for `style=`. If there is one, build on the hooks instead (`docs/security.md`, "What components do to live under the policy").
3. Write `app/components/<Name>.tsx`: one exported component with a small prop surface, each prop documented. Take colour, type, shape, spacing, elevation and motion from token utilities; use the shared pieces above for state, focus and motion. If it moves, give it a `motion-reduce:` class.
4. Add it to `app/routes/design.tsx` in every state it has.
5. Add a test to `e2e/components.spec.ts` that finds it by role and accessible name and operates it by keyboard alone. If it opens, add it to the list in `e2e/accessibility.spec.ts`; if it moves, operate it in `e2e/reduced-motion.spec.ts`.
6. Add a row to the table above.
7. Run `pnpm lint && pnpm test && pnpm test:e2e`.

## Shell

The application shell is everything under `/app`: a skip link, the navigation and the main region each destination renders into. The route is `app/routes/app/layout.tsx`; the parts are in `app/shell/`. The browser tests are `e2e/shell-*.spec.ts`.

### Destinations

`app/shell/destinations.ts` is the one list: Today (`/app`), Reports (`/app/reports`), Projects (`/app/projects`), Settings (`/app/settings`), in that order, each with its label, its address and the name of its Material Symbol. `app/routes.ts` builds the route tree from the list, the navigation draws it, the direction of a transition is the order of it, and the tests read their addresses from it. Nothing else writes one of these addresses. To add a destination, add it to the list, add `app/routes/app/<id>.tsx` with a `PageHeading`, and give its symbol a drawing in `app/shell/Navigation.tsx`.

Each destination's page is a placeholder until its own card: its heading and one sentence saying what will be there. Settings also holds the colour scheme.

### The 600px rule

One `nav` element with one list of links is drawn two ways, by CSS alone (rule 17). Tailwind's `medium:` variant is Material's medium window size, 600px (`--breakpoint-medium` in `app/app.css`); `max-medium:` is everything narrower.

| Window      | Navigation      | Where                            | Drawn from                                                     |
| ----------- | --------------- | -------------------------------- | -------------------------------------------------------------- |
| Under 600px | Navigation bar  | Along the bottom edge, 64px tall | `md-comp-nav-bar`, `md-comp-nav-bar-item-vertical`             |
| From 600px  | Navigation rail | Down the start edge, 96px wide   | `md-comp-nav-rail-collapsed`, `md-comp-nav-rail-item-vertical` |

An item is the same in both: a 56 by 32px active indicator around a 24px icon, a `label-medium` label under it, 64px tall in all. The active destination has `aria-current="page"`, the filled drawing of its symbol and the indicator. No script measures the window: the server sends the same HTML to every width, and the navigation works with script off.

### How a change of destination moves

React's `<ViewTransition>` (React 19.3) starts the browser's view transition when React Router commits a navigation; the animations are CSS in `app/app.css` and read the motion tokens. There is no `style` attribute in the HTML: React names the parts through the CSSOM when a transition starts.

- **Direction (rule 5).** A destination later in the list is forward of an earlier one. `useTravel` in `app/shell/transitions.ts` compares the destination arriving with the one on screen and gives the content the class `shell-forward` or `shell-back`. Going forward the old page leaves towards the start and the new one arrives from the end; going back is the mirror image. It works the same for a press on a destination, a link inside a page and the browser's Back button, because it reads only where the page was and where it is going.
- **Axis.** Under 600px the destinations lie side by side, so the content moves across. From 600px they are stacked, so it moves up and down. The distance is eight spacing units.
- **What moves (rule 6).** Only the content. The active indicator is one element with one view-transition name: it travels from the old destination to the new one on the spring. The icons of the two destinations fade, above the indicator.
- **The navigation is not in the transition.** The browser does not deliver a press to an element that is part of a running view transition, so the navigation stays an ordinary part of the page and can be pressed at any moment.
- **Interruption (rule 8).** React holds the next transition until the running one has finished. A press on a destination and the browser's Back and Forward therefore end the running transition first (`finishRunningTransition`, through `document.activeViewTransition`): its animations jump to their end and the new page arrives at once. In a browser without that property the next transition follows the running one, a third of a second later at most.
- **Only a change of destination starts a transition.** The content's `<ViewTransition>` has the class `none` in every other render. Without that, React starts a transition for any render that reaches it, and each one holds back the next navigation.
- **Reduced motion (rule 9).** Nothing moves or changes size: each part takes its new place at once and the content cross-fades.
- **A browser without view transitions** navigates with no animation.

### Focus and landmarks

- The first Tab stop is "Skip to main content", off the top edge until it has the focus. It moves the focus to the `main` element.
- Landmarks: one `navigation` named "Main" and one `main`. There is no top bar, so there is no `banner`.
- After a move between pages the focus is on the new page's `h1`, and the title has changed. Every page in the shell renders its heading with `PageHeading`, which can take the focus from script and is not a Tab stop. A screen reader announces the new page, and Tab carries on from its top. The same happens on arriving in the shell by a link from a page outside it.
- A page the browser loads whole leaves the focus alone.

### Colour scheme

Settings offers System, Light and Dark as one radio group. Light and Dark are stored in the cookie `__Host-color-scheme` (`docs/security.md`); System deletes it. The root loader reads the cookie and the server renders `data-color-scheme` on `html`, so a page arrives in the chosen scheme with no flash and no inline script. With script the choice is saved as it is made and the page changes without loading again; without script the form has a Save button and the page loads again.

### Locale

The root loader chooses a locale from `Accept-Language` (`app/shell/locale.ts`; `en-GB` when the request names none the server can format) and `app/root.tsx` gives it to React Aria's `I18nProvider`. Dates and numbers are therefore formatted the same way on the server and in the browser. The interface text is English and `<html lang="en">` does not change.
