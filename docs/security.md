# Security

The baseline every change is held to. Each control names the card that puts it in place, and that card's acceptance criteria prove it.

Timesifier holds personal data: who worked on what, and when. The owner is in the UK, so UK GDPR applies from the first real user.

## Authentication

Better Auth runs inside the Worker (`app/auth/auth.server.ts`) and answers every request under `/api/auth/`. The tests in `test/auth/` drive it through the Worker and hold what is written here in place.

### Flows

- **Email code.** A person asks for a code for an address; the request carries a Turnstile token. An eight-digit code is emailed. Sending it back, from the browser that asked, signs the person in and, the first time, creates their account with the address marked verified. The answer to "send me a code" is the same whether or not the address has an account. Signing in also leaves a proof in the browser that the address has been signed in from it (see "A browser that has signed in before").
- **Sign-out** ends the session the cookie belongs to. **Ending all sessions** ends every session the person has, this one included. Neither removes that proof.
- There are no passwords. Better Auth's password endpoints, like every endpoint the application does not offer, answer 404 (see "Endpoints").

### What is stored

| Table           | Holds                                                                                                                                                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`         | Name, email address, whether the address is verified                                                                                                                                                                                                                |
| `sessions`      | The session token, its expiry, the client address and user agent it was created from                                                                                                                                                                                |
| `verifications` | A keyed hash of each emailed code with its count of attempts, for five minutes; one row for each use of a cap (see "Abuse"), until that use stops counting; one row for each address with a code out, saying which request the code answers, for those five minutes |
| `rate_limits`   | One counter per client address and sign-in path                                                                                                                                                                                                                     |

How long these rows live: a code's row counts for five minutes and a cap's row for the hour or the 24 hours it counts in, and Better Auth deletes rows of `verifications` after they expire. A session lasts seven days and is extended while it is used; an expired `sessions` row stays until card TS-033 adds a daily job that deletes it.

These are the tables of signing in. Every table of the application, these included, is listed in `app/db/personal-data.ts` under the row of the privacy notice that says what it holds, and `test/claims.test.ts` fails when a table of `app/db/schema.ts` is in none. Nothing is deleted for its age except the rows this section names and the activity log's, which the daily job deletes after 730 days (`ACTIVITY_RETENTION_DAYS`, `workers/scheduled.ts`). Everything else of an organisation stays until it is deleted in the product or the organisation is.

A code is eight digits, works once, and stops working after three wrong attempts or five minutes. It is stored as an HMAC-SHA-256 under `BETTER_AUTH_SECRET` (`app/auth/keyed-hash.server.ts`), never as the code and never as a plain hash: there are few enough codes to try them all against a plain hash, so only the key makes a copy of the database useless on its own. The session cookie holds the token and a signature made with `BETTER_AUTH_SECRET`; the session itself is read from the database on every request, never from a copy in a cookie, so an ended session is refused at once.

### The cookie

`__Host-timesifier.session_token`, with `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` and no `Domain`. The `__Host-` prefix makes the browser accept the cookie only over HTTPS and send it only to the exact host that set it. Better Auth has no option for this prefix yet; how it is configured, and what to do when one arrives, is in `docs/decisions.md` entry 8. Do not rewrite the `Set-Cookie` header in the Worker: Better Auth would stop recognising its own cookie.

### A code is used in the browser that asked for it

The answer to a request for a code sets a second cookie, `__Host-timesifier.sign_in_code`, with the same attributes. Its value is an expiry, a random number that is that request's alone, and an HMAC under `BETTER_AUTH_SECRET` of the lower-cased address, the expiry and the number: it proves that this browser made this request for a code for this address, holds no address, and cannot be made or altered without the secret. The server keeps, for each address with a code out, the number of the request that code answers. A request to sign in with a code is checked against both before the email-code plugin sees the request (`app/auth/sign-in-code.server.ts`):

- no cookie, or one made for another address or altered: the answer a wrong code gets, `400 {"code":"INVALID_OTP"}`, byte for byte, and the code's three attempts are untouched;
- a cookie whose five minutes are over: the answer an expired code gets, `400 {"code":"OTP_EXPIRED"}`. The browser keeps the cookie for an hour so that this, and not "wrong code", is what a late person is told;
- a cookie from a request that the live code does not answer, because a later request took its place, or it was over its cap, or it was a stranger's while a known browser's code waited (see "Abuse"): the answer a wrong code gets, and the attempts are untouched.

So nobody but the browser whose request a code answers can use up that code's attempts. The first two were decided in `docs/decisions.md` entry 22. The third came with entry 27: until then the cookie proved only that a browser had asked for some code for the address in the last five minutes, and every request was given one, so anybody who asked could spend the three attempts of a code sent to somebody else's request.

### A browser that has signed in before

When a code signs a person in, the answer sets a third cookie, `__Host-timesifier.known_browser`, with the same attributes and a `Max-Age` of one year (`app/auth/known-browser.server.ts`). Its value is one proof for each of the last five addresses signed in from that browser, newest first: a proof is an HMAC under `BETTER_AUTH_SECRET` of the lower-cased address, made for this purpose alone. The cookie holds no address and a proof cannot be made without the secret. A changed proof, a proof for another address and no proof are all the same: a stranger.

The proof signs nobody in. It decides two things about a request for a code, both under "Abuse": which of the address's two counts the request falls in, and whether the request may replace a code that is waiting. Nothing in the answer to a request says which it was taken for.

Signing out and ending all sessions leave the cookie alone. A person who has signed out is who asks for a code next, and ending every session cannot reach a cookie held by another browser. A proof is the same in every browser and carries no date, so one cannot be withdrawn short of changing `BETTER_AUTH_SECRET`; what a proof in the wrong hands allows is in "Known gaps".

### Hosts

The hosts are per environment, and no host is written in the code: a deployment names its own in its settings (`app/auth/hosts.ts`; "Secrets" below). `ENVIRONMENT` is `production`, `preview` or `development`. Production trusts the one host in `APP_HOST`, a preview trusts hosts ending with `PREVIEW_HOST_SUFFIX` (`-<worker>.<account>.workers.dev`), and `development`, which is a developer's machine or a test, trusts `localhost` on any port. Better Auth takes the application's address and its trusted origins from the request only when the host is one of the environment's own. A request for any other host gets 404 from the mount before Better Auth sees it: no cookie is set and no session is read.

None of the three has a default. Where `ENVIRONMENT` is missing or is any other word, where production has no `APP_HOST`, or a preview no `PREVIEW_HOST_SUFFIX`, or where either is not exactly a host name or a suffix of that form (Better Auth reads a host it is given as a pattern, so `*` or `*.com` would otherwise be trusted), nothing is guessed: every sign-in request and both sign-in pages answer 500, and the log names the setting. `test/deployment.test.ts` takes each setting away and holds this in place.

No request can name a place to send the browser other than a path on its own origin: a `callbackURL`, `redirectTo`, `errorCallbackURL` or `newUserCallbackURL` that is anything else gets 403 (`app/auth/redirects.server.ts`).

### Endpoints

`app/auth/endpoints.ts` lists the 20 endpoints the application offers under `/api/auth`, each with its one method: asking for a code and signing in with it; the session, sign-out and ending all sessions; and 15 for organisations. They are the ones a page calls and no other: an endpoint nothing calls is not offered, however harmless. Any other method or path gets 404 from the mount before Better Auth, its rate limit or the database sees the request, so an unknown path costs no read and no write. Better Auth registers 63 endpoints under this configuration, among them a health check, an error page of its own and one that sets a person's name and image; none of those is reachable. `test/auth/endpoints.test.ts` reads every endpoint from the installed library and fails when one is neither listed nor answered 404, so an upgrade cannot add one unnoticed. The two code requests take exactly their own fields: a code of any kind but `sign-in`, an image for a new account, or any field that is not listed gets 400. Signing in with a code may carry the name a person gave on the sign-up page, which is stored when the code creates their account: one line of at most 100 characters, with no control character and none that reverses the direction of text.

### Abuse

- **Rate limit.** Counted in D1 per client address and path. The address is `CF-Connecting-IP`, which Cloudflare sets and a client cannot forge; `X-Forwarded-For` is ignored. One client may ask for a code 3 times a minute and try to sign in with a code 10 times a minute; the next request gets 429. The count starts again 60 seconds after the last request that was let through. The limit applies only to requests that arrive at `/api/auth/`: server code that calls Better Auth directly is not limited, so sign-in must never be offered through another route.
- **Codes per address.** An address is sent at most 5 codes in any hour to browsers that hold a proof of having signed in as it, and at most 5 to everybody else, from wherever they ask (`docs/decisions.md` entry 27). Somebody who knows only the address can therefore use up the second count and not the first. A request over its count is answered exactly like a served one and nothing is issued or sent, so neither count tells anybody that an address has been asking. With three attempts a code, that is 15 guesses an hour from strangers against a hundred million codes, and 30 in all. The counts are kept in `verifications` under an HMAC of the address, not the address (`app/auth/quota.server.ts`), and a request that the rate limit or Turnstile refused is not counted.
- **A waiting code.** The email-code plugin answers every request with a new code and compares a guess with the newest alone (`resolveOTP` and `atomicVerifyOTP` in `plugins/email-otp/routes.mjs`, Better Auth 1.7.19), so any request replaces the code before it. While the code of a browser that has signed in before is waiting, which is at most five minutes and ends when the code signs the person in, a stranger's request therefore never reaches the plugin: it is answered like a served one, takes one of the strangers' five, and issues and sends nothing. A browser that has signed in before replaces its own waiting code by asking again, and a stranger's request replaces another stranger's.
- **Turnstile.** The token is sent in the `x-captcha-response` header and verified with Cloudflare before a code is created. A missing token gets 400 and a rejected one 403; neither creates nor sends a code. The hostname in Cloudflare's answer, the site the token was solved on, must be the host of the request itself, in production and on a preview (`app/auth/turnstile.server.ts`, through the captcha plugin's `allowedHostnames`). The production widget is registered at Cloudflare for `timesifier.com` only, so this is a second layer, not the only one. Cloudflare's published test secrets always answer with the hostname `example.com`: that hostname is accepted when the configured secret is one of those test secrets, and never otherwise.

### The guard on `/app`

Everything under `/app` needs a session. The layout route `app/routes/app/layout.tsx` exports a `middleware` (`requireSession` in `app/routes/auth/session.server.ts`) that reads the session with `getSession`, from the database, before the loader or action of any route under it runs. Without a session that is still valid it answers with a redirect to `/sign-in?next=<the address asked for>`: a 302 for a page, and the framework's encoding of the same redirect for a data request. An action behind the guard does not run. The layout also exports a `loader`, so that every move between destinations asks the server and passes the guard; an ended session is turned away on the next move, not only on the next page load.

- **A new route under the layout is covered by being there.** `test/auth/guard.test.ts` reads every route whose address is `/app` or below it from the built route configuration and requests each one without a session: the page, its data, and a form posted to each route that has an action. A route placed under `/app` but outside the layout fails that test.
- **Loaders and actions under `/app`** read the signed-in person from the router context (`signedInContext`), which the guard sets. They do not read the cookie again.
- **`next` is never trusted.** After sign-in a person goes to `next` only when it is a path on our own origin at or under `/app`, or the page of one invitation; anything else, or nothing, gives `/app` (`safeNext` in `app/routes/auth/paths.ts`). The value is parsed as a browser would follow it, so an address behind `//`, a backslash or `..` is judged by where it leads. The sign-in page sends a person who already has a session to the same place.
- **The page calls Better Auth only through `/api/auth/`**, from the browser, where the rate limit and the Turnstile check act. No message on it says whether an address has an account.

### The pages for a person who is signed out

The home page is for a person who is not signed in, and is never shown to one who is (card TS-055). `app/routes/home.tsx` exports a `middleware`, `requireSignedOut` in `app/routes/auth/session.server.ts`, that reads the session as the guard on `/app` does and answers a person who has one with a redirect to `/app`, which sends them on to their organisation: a 302 for the page, and the framework's whole-page redirect for a data request. The route also has a loader, so a move to it from inside the application asks the server too. The sign-in page's loader does the same, to `next`. Only signing out, or a session that has ended, shows these pages again.

- **A failure is not proof of being signed out.** When the session cannot be read, the request gets the error page, not the home page.
- **No copy of a page is kept.** Every HTML response, and every `.data` response a move between pages loads, is sent with `Cache-Control: private, no-store` unless it says otherwise itself (`workers/no-copy.ts`). Neither the browser nor anything between keeps a page seen before signing in or after signing out.
- **The back button asks the server.** A page the browser restores whole from its back-forward cache reloads at once (`app/shell/fresh-on-return.ts`, in the root route), so the server decides again: back from the application does not reach the home page, and back after signing out does not reach the application.
- **Tests.** `test/pages/signed-out-pages.test.ts` (redirects, the data request, signing out, a session that cannot be read, the headers) and the journey "the home page and the session" in `e2e/auth-journeys.spec.ts`, which walks back through a tab's whole history in both engines.
- **Not covered:** the privacy notice and the terms are documents for everyone, signed in or not, and stay open to both.

### One way in

`/sign-in` is the one page a person uses without a session, new or returning (card TS-036). The email-code plugin makes the account of an address the first time a code proves it, so the page asks nothing that tells the two apart, and says nothing that does.

- **No name on the way in.** `POST /api/auth/sign-in/email-otp` takes `email` and `otp` and nothing else: a request with a `name`, an `image` or any other key gets 400 (`app/auth/sign-in-code.server.ts`). An account begins with no name; a person is shown by their address until they set a name in Settings, which is validated by the one rule for a name.
- **`/sign-up` is not a page.** A `GET` or `HEAD` for it is answered by the Worker before the framework (`workers/former-sign-up.ts`), after the host and origin checks: status 302 to `/sign-in`, keeping `next` when `safeNext` allows it and dropping every other query, the same for a person with or without a session. It is 302 and not a permanent redirect so that no browser holds it for good. Any other method reaches the framework, which has no such route. `sign-up` stays among the reserved organisation slugs.
- **The wrong address makes an account.** A person with two addresses who signs in with the other one, or with one that is theirs and misspelt, proves it and gets a second, empty account: that follows from one page for everybody, and nothing can tell them from a new person. (An address nobody can read makes nothing: an account is made when a code is used, not when one is asked for.) So the two pages such an account lands on say whose account it is and offer "Use a different email", which signs out and loads `/sign-in`: on `/app/new` the profile menu is named after the address, shows it, and holds that one item (`app/shell/ProfileMenu.tsx`); an invitation that is not this account's says "Signed in as" with the address at its foot and keeps `next` (`app/routes/app/SignedInAs.tsx`). An invitation's "no longer valid" page shows the reader their own address and still nothing of the invitation.
- **A code that was asked for is remembered by its tab.** The page keeps the address and the time in `sessionStorage` under `timesifier.sign-in-code`, for the five minutes a code works, so a reload or a return from the mailbox finds the view that takes the code (`app/routes/auth/pending-code.ts`). It is cleared when the person signs in, asks to use a different email, or the five minutes pass. It holds no code and no token, it is this tab's alone, and a code still works only in the browser whose cookie asked for it. Besides cookies it is the only thing our own code stores in the browser; React Router keeps how far each page was scrolled in `sessionStorage` too, under `react-router-scroll-positions`. The privacy notice names both.

### Email

`sendEmail` in `app/auth/email.server.ts` is the only code that touches the `EMAIL` binding. Every message comes from the platform brand's sender name (`Timesifier` until it is changed) and the one address in the deployment's `EMAIL_FROM`, and the deployed configuration allows the binding that sender and no other. The sender name and the Reply-To are read from `platform_brand` as each message is sent; `setPlatformBrand` accepts a sender name only without `< > " @ , ; : \` or a line break, and a Reply-To only as one plain address, so neither can add a header or a second recipient. A Worker that has the binding and no valid `EMAIL_FROM` does not build Better Auth, so it answers no sign-in request.

Every message is built by one frame, `compose` in `app/auth/email-frame.ts` (TS-100). Its images, the platform's logo and mark and an organisation's logo, are attached to the message inline, as PNG or JPEG, and the HTML refers to each by its Content-ID (`cid:`): nothing in a message is fetched, so opening one tells nobody it was opened. No message carries a remote image, style sheet, font or tracking address, and the code email no link (`test/auth/email-frame.test.ts`, `test/brand/documents.test.ts`, `test/claims.test.ts`). Sending is handed to `waitUntil`, so how long it takes does not show in the response. A preview has no `EMAIL` binding and sends nothing; locally Wrangler simulates the binding and sends nothing either.

### Never logged

No log line carries an email address or any part of one, a code or its hash, a cookie or a session token. The email sender logs nothing about the recipient, and the error code of a failed send without its message. An error nobody expected, a statement D1 refused for one, is answered `500 {"code":"INTERNAL_SERVER_ERROR"}` and logged as its name and the endpoint's path, without the query string: Drizzle's message for such an error is the statement with its parameters. Better Auth's own logger is replaced by one that keeps the library's words up to the first colon and the name of any error it was handed (`app/auth/log.server.ts`), and `getSession` throws an error of its own in place of the library's, which carries the statement. `test/auth/email.test.ts` reads every line logged during a whole sign-in, and during a failed statement on each of three tables, and fails if one of those values appears.

Outside authentication the rule is held by `handleError` in `app/entry.server.tsx`, which React Router calls for every error it catches on the server, in a loader, an action, a middleware or while rendering. It writes the error's name and the path, with each parameter of the path written as its name (`/invitations/:id`), and never the message or the query string; a request the browser gave up on is not logged. `test/error-log.test.ts` holds it in place.

### The one action without `parseRequest`

`app/routes/api.auth.$.ts` hands the request to Better Auth untouched. Better Auth checks each endpoint's body against its own Zod schema and answers 400 for a body that is not JSON or does not match, and 415 for a content type other than JSON; reading the body first with `parseRequest` would consume it. `test/action-validation.test.ts` holds the 400 in place like any other action.

## Organisations and roles

Better Auth's organization plugin keeps organisations, memberships and invitations in our tables, and is configured in `app/auth/organisations.server.ts`. It is reached through the same mount, at `/api/auth/organization/*`. The tests in `test/organisations/` drive it through the Worker and hold what is written here in place. Teams, and roles made up at run time, are switched off.

### Roles

A member of an organisation is an owner, an admin, Finance or a member. The roles and what each may do are in `app/organisations/roles.ts`, which the plugin checks on the server for every request; nothing a browser sends decides it. Finance (TS-064) has exactly a member's plugin permissions: what sets it apart is what it is shown inside the organisation, below.

| Action                                                   | owner                      | admin                | finance | member |
| -------------------------------------------------------- | -------------------------- | -------------------- | ------- | ------ |
| See the organisation and its members                     | yes                        | yes                  | yes     | yes    |
| Rename the organisation                                  | yes                        | yes                  | no      | no     |
| Delete the organisation                                  | yes                        | no                   | no      | no     |
| Invite a person                                          | yes                        | yes                  | no      | no     |
| Cancel an invitation                                     | yes                        | yes                  | no      | no     |
| Change a member's role between admin, Finance and member | yes                        | yes                  | no      | no     |
| Make another person owner, or change an owner's role     | yes                        | no                   | no      | no     |
| Remove a member                                          | yes                        | yes, except an owner | no      | no     |
| Leave the organisation                                   | yes, unless the last owner | yes                  | yes     | yes    |

An organisation always has at least one owner: the last owner cannot leave, be removed or be demoted. A member holds exactly one role; a request that names a list of roles, or a role that is not one of the four, gets 400. An owner or admin gives Finance by inviting a person as Finance or by changing a member's role to it. Whether a person is an employee or a contractor is `memberships.is_contractor`, set by an owner or admin (TS-079); it grants nothing. An owner marks anyone, themselves included; an admin marks anyone whose role they may change, so neither an owner nor themselves (`mayMarkContractor` in `app/contractors/contractors.ts`). Anybody else is refused with 403, or the 404 of Team where they are not shown it, and nothing changes; each change is recorded in the activity log as `membership.contractor_changed`. Pending invitations are shown only to those who may invite, because an invitation's id is its link.

`test/organisations/permissions.test.ts` holds a copy of this table and has a trial through the real endpoint for each of its 36 cells; it fails when a cell has no trial or a trial contradicts its cell. Change the table here, in the test and in `roles.ts` together.

Clients is hidden from everyone while the organisation has `clients_enabled` off. A destination a person is not shown answers 404 at its address and at every address below it, for a page, a data request and a form alike: the organisation layout's second `middleware` reads the destination from the pattern of the route that matched, so no spelling of an address reaches a page by another route, and the 404 is the one a stranger gets (`test/pages/destinations.test.ts`). Finance sees that a person is off but not the kind of their leave (`maySeeLeaveKindOf`: the person, owners, admins and the managers of their teams), and decides no leave.

Every role creates, renames, archives and restores projects; nobody deletes a project or a client (TS-011a). Owners and admins, while Clients is on, manage clients and give a project its client (`mayManageClients`): the Projects action answers 403 to anyone else who sends a client, and a client that is archived or of another organisation is never given (TS-011b). Finance is shown Clients, to invoice them, and reads it: the page offers it nothing to press, and the Clients action answers its forms 403 (TS-075). The general settings, the default time zone, the week start and the Clients switch, are an owner's or an admin's (TS-048), and so is the policy for leave: the working week, the kinds of leave, their allowances and whether they need approval, and the public holidays (TS-061, `mayManageLeavePolicy`): nobody else is shown Workspace settings, and its action checks the role again; an action naming a project or client of another organisation answers 404 and changes nothing (`test/pages/projects.test.ts`, `test/pages/clients.test.ts`).

Every route of an organisation has a row in the role table of `test/pages/finance.test.ts` (TS-075): the status of its page and its data to an owner, an admin, Finance, a manager and a member, and for each route with an action a form and whether each of them is allowed it, with nothing changed when refused. The table is read against the built routes, so a route added without a row, or an action without a form, fails it. The same file holds every rule of `access.ts` for each kind of person, a Finance person who manages a team among them.

### Whose time

`app/organisations/access.ts` holds the rules inside the destinations, and `accessOf` reads what they take on every request. A person sees, adds and changes their own entries and submits their own periods. An owner or admin sees everyone's time, decides everyone's periods and alone reopens an approved one. Finance sees everyone's time and expenses, read-only, and decides nothing: no period, unless they manage a team, and then as a manager. A manager sees the time of the members of the teams they manage and decides their periods, never their own. Nobody changes another person's entries (decision 25), and expenses follow the same rule: `maySeeExpensesOf` gives the people of `timeScopeOf`, `mayChangeExpensesOf` the person alone. A list or report passes the people it may hold to SQL (`timeScopeOf`); it never filters afterwards.

Teams (TS-038) are made, renamed and deleted, filled and given managers by an owner or admin alone, on Team > Teams; a manager sees the teams they manage there and changes nothing, and the server refuses their form with 403. Only a member of the organisation can be put in one of its teams. A person taken out of a team, or no longer its manager, loses what it gave them on their next request, because `accessOf` reads the teams on every request. Approvals (TS-047) changes a period only through `statusAfter`, and writes the period and its `period_events` row in one batch, with who decided and when.

Leave (TS-061) follows the same lines, in `mayDecideLeaveOf`, `mayCancelLeaveOf` and `maySeeLeaveKindOf` in `app/organisations/access.ts`. A person asks for their own leave and withdraws their own request while it waits. A request is approved or refused by a manager of a team the person is in, or by an owner or admin, and never by the person themselves, whatever their role; sick leave, and any kind set to need no approval, is approved as it is made. A request already decided, withdrawn or cancelled is not decided again: the action answers 409 and changes nothing. An owner or admin alone cancels approved leave that has not begun, with a reason of 1 to 500 characters, and never their own. Everyone in the organisation may be told that a colleague is on leave; the kind of leave is told only to the person, the managers of their teams, and owners and admins, the people who may see their time. Anybody else is shown "On leave": `leaveOfPeople` replaces the kind's name before the rules read the request, so no label made from it holds the kind. Today every page that shows another person's leave, Team's week, Approvals, Time off's Requests and Reports, lists only people whose time the viewer may see. Leave is never added to worked time. Its four tables, `leave_kinds`, `leave_requests`, `public_holidays` and `working_days`, are in `tenantTables` and reached only through `organisationScope`; a request's kind and its person are pairs of columns with the organisation, so the database refuses a request of another organisation's kind or for somebody who is not a member (`docs/architecture.md`, "Tables"). A request, a kind or a public holiday of another organisation named in a form is not found: the action answers 404 and changes nothing, and a request for leave of such a kind is refused.

Work schedules (TS-097, `routes/app/schedules.tsx`) are created, changed, archived and assigned by an owner or admin alone, on Settings › Work schedules, which answers 404 to anybody else, and the action refuses them again; every change is dated today or later, so no past day's expected hours, leave or overtime change. A manager sees the schedules of the people they may see on Team, read only; every person sees their own on My account and through the API's `GET /work_days`, which lists only people whose time the token's maker may see. Every change is in the Activity log; an assignment to a person is theirs there.

Requests for overtime and weekend work (TS-090, `app/leave/work.server.ts`) follow leave's rules exactly: a person asks for and withdraws their own; `mayDecideLeaveOf` decides who approves or refuses, never the person; `mayCancelLeaveOf` who cancels one approved that has not begun; a person nobody else can decide for has theirs approved as it is made. They can be asked for only while the organisation's overtime rule is "only with pre-approval" (weekend work only while days not worked count as overtime), which owners and admins set in Workspace settings with the notice rule; each change of the rules is in the activity log (`timesheet_rules.changed`), as is each timer cut at a day's limit (`time_entry.split`). Whether time is overtime is checked on the server on every path, the API and a CSV import included: regular time past a day's expected hours, and overtime the rules do not allow, past a cap or past what was approved, are refused with what is left (TS-095). The limits they raise are checked on the server by every writer of time entries before it writes, whatever the browser shows: a request the page would have stopped is refused with the same words. The team's leave to come on Time off names the kind only where `maySeeLeaveKindOf` allows; anyone else reads "On leave".

A report and its export (`app/reports/reports.server.ts`) read the people of `timeScopeOf` as one JSON parameter, so a manager of many people stays inside D1's limit on bound parameters. A report narrowed to one person names them in its address; a person the viewer may not see, or who is not a member, gets the same 404 as another organisation's address. A cell of the export that a spreadsheet would read as a formula, one that starts with `=`, `+`, `-`, `@`, a tab or a carriage return, is prefixed with `'` (`app/reports/csv.ts`).

Each project's hours on Projects (TS-057, `projectHours` in `app/projects/projects.server.ts`) are added up in SQL over the people of `timeScopeOf`, passed the same way, so every role sees every project but only the time it may see: an owner, admin or Finance everyone's, a manager their own and their teams' people's, a member their own; the page's sentence says which. They are one statement, `organisationScope`'s `sum`, which keeps the organisation's condition outside the caller's filter as `select` does. The words searched for on Projects and Clients are bound as one parameter and matched with `instr`, so `%` and `_` are letters.

### Rates and money

Rates and the amounts made from them, billable and cost rates, billable amounts, budgets in fees, profitability, invoices, estimates and payments, are seen and set by owners, admins and Finance alone (`maySeeRates`, `mayManageRates`, `mayInvoice`), never by a manager: the owner decided so on 2026-11-11, against Harvest's rate permission for managers. A page or report that holds money checks `maySeeRates` on the server and leaves the money out of what it sends; a column is not hidden in the browser. A budget in hours is shown to those who see rates and to managers; a budget in fees only to those who see rates; a member is only warned, on Track time, when the project is over a budget whose people are warned (TS-069). A budget's alert goes once a period, its `budget_alerts` row's unique index letting one write through, to owners and admins and, for a budget in hours, the managers of the people who tracked to the project; its subject and heading hold nothing anybody typed. The default rates (`projects/rates`) answer the in-shell 404 to anybody who does not see rates, page, data and form alike, so a manager or member learns nothing of them; a project's page is everyone's, and its forms check the role of each change: billing, budget and rates `mayManageRates`, its tasks and tags `mayManageTasks`, 403 to anybody else, and 404 for a project of another organisation (`test/pages/money-pages.test.ts`). A rate starts today or later, so no entry already tracked is priced again (TS-067). A change of what is billed, a task made billable or not on a project or the project's type, changes only the entries no invoice bills (`invoice_line_sources`); an invoiced entry keeps what it was billed as (`test/pages/money-rules.test.ts`). Tasks and tags are an owner's or admin's (`mayManageTasks`): Tasks, with its Tags list, is shown to nobody else and answers them 404. A task or tag is archived, never deleted: an archived one is put on nothing new, and stays on what has it. A person puts tags on their own entries alone, as with every change to time (decision 25). Tag and task names are unique in the organisation by a case-folded key, which a unique index holds. API tokens and webhooks are an owner's or admin's too (`mayManageIntegrations`).

Cost, what a person's time costs at their cost rates, is money too. The Contractors report (TS-079, `reports/contractors` and its CSV at `reports/contractors/export`) lists each contractor's hours and cost, and is seen by owners, admins and Finance alone: each of its two routes has a middleware (`requireSeesCost` in `app/contractors/contractors.server.ts`) that throws the organisation's 404 before any loader runs, so a member or a manager, who is shown Reports, gets the same answer there as a stranger, and nothing of the report is read. Who is a contractor is not money: a member's row on Team › Members says "Contractor" to whoever is shown Members. A person who left keeps their entries; whether they were a contractor is read from the activity log's record of their leaving (`membership.removed`, whose `before` holds `isContractor`), so it is known for as long as the log keeps that record (730 days).

### Locks

An entry, an expense or a day of leave is locked, and refused to everyone who would create, change or delete it, for any of three reasons, which `app/locks/locks.ts` names: it is on or before the organisation's lock date (`organisations.locked_through`), which binds everyone, the owner included, until an owner or admin moves the date back (TS-065); it starts in a period that is submitted or approved (TS-046); or it is on an invoice line (`invoice_line_sources`), until the line or the draft is deleted or the invoice voided (TS-073). A lock is worked out on every write from those rows and never stored.

The lock date is set, moved and removed on Workspace settings › Timesheet locking, by an owner or admin alone (`lockAction` in `app/locks/settings.server.ts`); anybody else gets the 404 of Workspace settings, its forms included, and `lockAction` asks again (403). A date after today in the organisation's zone is refused, and so is moving the date back, or removing it, without a reason. The change is written with a compare-and-set on the old date, so of two owners changing it at once the second is told it changed (409), and its activity record follows it. The lock date's reason is kept in that record (`after.reason`), the one stated exception to the rule that free text is never copied there: it is an administrator's statement about the organisation, not anybody's description of their work, and it is shown to everyone the date stops, on the Day and Week views. The timesheet deadline, auto-lock and auto-submit are set in the same section by the same people. Auto-lock (`runAutoLock`, hourly) only ever moves the date forward, once per deadline, and auto-submit submits unsubmitted periods as the system: their `period_events` row has a null `actor_id`, which means the system, and the activity record a null actor with source `system`. Writers refuse a locked change on the server whatever the page offers: time entries (`app/time/manual.server.ts`, which also refuses an invoiced entry) and leave (`app/leave/leave.server.ts`); expenses are to call `lockReasonsOn` and `invoicedIds` from their own writers.

### API tokens

An owner or admin creates a token on Integrations (TS-081). It is shown once, when it is made, and starts `tsf_`; the database holds a keyed hash of it under `BETTER_AUTH_SECRET` with the purpose `api-token` (`app/auth/keyed-hash.server.ts`, `app/integrations/tokens.server.ts`), and lists show only its first 8 characters. A token carries the scopes chosen when it was made (`app/integrations/scopes.ts`), records when it was last used (to the minute, so a busy token costs one write a minute), may have an expiry, and is revoked at once by an owner or admin; a revoked or expired token gets 401, as does one whose maker has left the organisation.

A token acts as the person who made it, with their role and teams read again on every request (`app/integrations/caller.server.ts`), so it never reaches more than they could on the pages, and its scopes narrow that further: whose entries, expenses and people (`timeScopeOf`), the kind of a person's leave (`maySeeLeaveKindOf`), money (`maySeeRates`, `mayInvoice`), Clients (`canSee`). A token writes its maker's own entries and nobody else's, through the Timesheet's own functions, so the same locks hold; each write is in the activity log with the source `api`. Entry descriptions and expense notes travel only with the scope `descriptions:read`. Each token may make 100 requests in any 15 seconds (`API_RATE_LIMIT`, counted in `verifications` like the other caps in `app/auth/quota.server.ts`); the next is answered 429 with `Retry-After`, the seconds until the oldest request stops counting. The API takes no cookie and is not a browser's: a request with a foreign `Origin` that changes state is refused 403 by the origin check before the API sees it. `docs/api.md` describes it.

### Webhook secrets

A webhook's secret is derived from `BETTER_AUTH_SECRET`, the webhook's id and its version, shown once and never stored; the row keeps only a hash of it (`webhooks.secret_hash`). Each delivery carries a header `Timesifier-Signature: t=<unix seconds>,v1=<signature>`, where the signature is HMAC-SHA-256 under the secret of the timestamp and the body, so a receiver can refuse a replay. Rotating the secret raises `secret_version`, after which deliveries are signed with the new secret alone (TS-087).

A webhook's address must be `https` and name a public host by name: no IP address, no `localhost`, `.local` or `.internal`, no user name or password, and not Timesifier's own host. A delivery does not follow a redirect and is given 10 seconds. A delivery holds what the webhook's maker would read through the API with the scope `time:read`, as they are when it is queued: an event about someone they may not see is not sent, and an entry's description, or an expense's notes, only when the webhook was added with descriptions. The `changes` it carries are the activity record's, in which a description is only ever "changed". A delivery that is not answered 2xx is tried again after 1, 5, 30, 120, 360 and 720 minutes; after its seventh attempt it fails, and after three failed deliveries in a row the webhook is switched off and its maker is emailed (`app/integrations/webhooks.server.ts`).

### Calendar feeds

A calendar feed's address holds a secret, `cal_` and 43 base64url characters (256 bits); the database keeps a keyed hash of it with the purpose `calendar-feed`, and the address is shown once (TS-089). The address answers 404 alike when it was never made, when it is revoked, when its person has left, and when a team's manager no longer manages the team. A person's own feed lists their approved leave and, if they chose, their entries of the last 90 days with their descriptions; a team's feed lists its members' approved leave by name, the kind only where `maySeeLeaveKindOf` allows, and no entry and no words. The feed is sent `Cache-Control: private, no-store` and `X-Robots-Tag: noindex`.

### Imports

An owner or admin imports time, clients or projects from a CSV of at most 1 MB and 5,000 rows (TS-076). The file is kept in `import_jobs.source` only while it is previewed, and emptied when it is imported; the rows it skipped are kept by line and reason, never with their notes. People are never created: a row is matched to a member by email, or by a name that exactly one member has. Reverting deletes only entries carrying the import's id, and refuses while any of them is locked (`app/locks`). The export of all time writes each cell through `csvCell`, so a value that a spreadsheet would read as a formula is written as text.

### Activity log

`activity_records` is only added to: the application has no update or delete of it apart from the retention job, and migration `0008` holds a trigger that refuses any UPDATE. Each record names the actor (null for the system), the source (`web`, `api`, `import` or `system`), the action, the subject, the person whose record it is about (`owner_id`) and the fields before and after (`app/activity/activity.server.ts`). Descriptions, notes and comments are never copied: a changed description is recorded as changed, not as what it said. The lock date's reason is the one exception (see Locks). Who reads which records is `activityScopeOf`, applied in the query itself (`app/activity/log.server.ts`), never by filtering afterwards: owners, admins and Finance every record; a manager their own and their teams' people's; a member their own; records about the organisation's own things, which are nobody's (the lock date, the deadline, projects, clients), only those who read every record. The Activity log page (TS-072), its CSV export and an entry's history (`/app/<slug>/history?entry=<id>`) all read through that one scope; an entry the reader may not see is the same 404 as one with no record. Records are kept 730 days (`ACTIVITY_RETENTION_DAYS`), then deleted by the Worker's scheduled handler (`workers/scheduled.ts`, daily at 03:17 UTC, `deleteExpiredActivity`), the only delete of the table; the trigger refuses UPDATE alone. TS-020's security events are a separate table with their own retention.

The money records are all the organisation's own, so nobody's: rates (a cost rate too, though it is a person's), budgets, invoices, payments and write-offs, sends, estimates, recurring invoices, retainers and expense categories. A manager therefore never reads a rate or an amount in the log; owners, admins and Finance do. Each is written in the batch that makes its change, and a change that may find nothing left to do (an invoice issued or voided twice at once, an estimate answered twice) writes its record only while the change is still to be made, so it is recorded once (`recordStatementWhen`). An import records each entry, client, project and task it adds, and each entry a revert deletes, with source `import`; the API's entry writes carry source `api`.

### Receipts

An expense's receipt is stored in R2 under a key scoped to the organisation, `org/<organisation id>/receipts/<expense id>`, built on the server from the expense's row and never taken from a request. It is served through the Worker only to a person who may see the expense (`maySeeExpensesOf`); anyone else, in this organisation or another, gets the same 404 (TS-070). A receipt is accepted only as a PDF, PNG or JPEG of at most 10 MB, judged by its first bytes as well as its declared type; its file name is cleaned of control characters, quotes and path parts before it is kept, and it is served with its stored type, `nosniff` and a policy under which nothing loads. Only `app/expenses/receipts.server.ts` reaches the `RECEIPTS` binding.

A receipt is deleted from R2 when its expense is deleted, when its expense's receipt is removed or replaced, and when its organisation is deleted. Before an organisation's row goes, `beforeDeleteOrganization` (`app/auth/organisations.server.ts`) lists every key under `org/<organisation id>/receipts/` a page at a time, following R2's cursor, and deletes each page in one call (`deleteOrganisationReceipts`). If any of it fails the organisation is not deleted: the request is answered 503 with the code `RECEIPTS_NOT_DELETED`, Workspace settings says the organisation was not deleted and to try again, and asking again deletes what is left and then the organisation (`test/db/delete-organisation.test.ts`). The R2 bucket has the `eu` jurisdiction (`wrangler.jsonc`): "Jurisdictional Restrictions guarantee objects in a bucket are stored within a specific jurisdiction" ([Cloudflare, R2 data location](https://developers.cloudflare.com/r2/reference/data-location/)).

### Organisation logos

An organisation's logo (TS-100) is stored in R2 under `org/<organisation id>/brand/logo`, and the PNG the browser drew from an SVG or a WebP beside it under `org/<organisation id>/brand/logo.png`: keys built on the server from the organisation of the request, never taken from it. Only its owners and admins may upload, replace or remove it, on Workspace settings › Brand; anybody else, in the organisation or not, gets the same 404 as for the page, and nothing is stored (`test/brand/logo.test.ts`). Each change is recorded as `brand.changed` on the Activity log, with the kind of file before and after.

A logo is accepted only as a PNG, JPEG, WebP or SVG of at most 256 KB and 16 to 2048 pixels a side, judged by its first bytes, which must agree with the type the browser gave, and by the size its own bytes state (`app/brand/images.ts`). An SVG is refused, not cleaned, when it could do more than draw: a script, an event handler, an embedded document, an animation, a document type or entity, a processing instruction, a style sheet's import, a `javascript:`, `vbscript:` or `data:` address, or any address but a fragment of the file itself. The PNG drawn from it must itself be a PNG under the same limits. Only a PNG or a JPEG is ever put in an email or a PDF; an SVG never is.

The logo is served through the Worker with its stored type, `nosniff` and a policy under which nothing loads: to every member at `/app/<slug>/logo`, and to a client at `/estimate/<id>/<token>/logo` only with the estimate's own token, a wrong token being the same 404 as no logo. Only `app/brand/organisation-brand.server.ts` reaches the `BRAND` binding. Deleting an organisation deletes its objects in `BRAND` before its row; should a delete fail, the organisation is not deleted and says so, and asking again deletes what is left.

### Invoices, estimates and payments

Invoices, Estimates and every page below them (TS-073, TS-074, TS-077, TS-078, TS-088) are owners', admins' and Finance's alone: the organisation layout's destination check answers anyone else 404 at every address under them, for a page, a data request, a PDF, a CSV and a form alike (`test/billing/invoices.test.ts`, `test/pages/destinations.test.ts`). A page of one record, `/invoices/<id>`, `/estimates/<id>` and their PDFs, reads the record through `organisationScope`, so another organisation's id is the same 404 as one that does not exist (`test/pages/isolation.test.ts`, which expects 404 at the stand-in id of every such page).

The database holds the rules a race could break (migration `0009_billing`): an invoice's or estimate's number is read from the organisation's sequence inside the D1 batch that stores the document and raises the sequence, so two saves at once never share a number and a deleted draft's number is not given again; a time entry or expense is on at most one invoice line (a unique index), and a trigger refuses any change to one that is; another refuses inserting, changing or deleting lines of an issued invoice; another refuses a payment or write-off larger than the balance; and a retainer's balance cannot go below 0. Deleting a line or a draft, or voiding an invoice, lets go of what it billed for.

Every statement goes through `organisationScope` (`app/db/scope.ts`). Its `exists`, `value`, `insertIfAbsent` and `insertWhen` build the subqueries and guarded inserts billing needs (the next number, the settled status from payments, a retainer's deposit once its funds invoice is paid), each limited to the organisation like every other accessor. Three reads cross organisations on purpose and are named in `app/db/unscoped.ts`: the templates due and the organisations sending reminders, for the hourly scheduled run, which has no person to start from; and an estimate by id for its public link.

An estimate's public link, `/estimate/<id>/<token>`, carries a token that is a keyed hash of the estimate's id under `BETTER_AUTH_SECRET` with its own purpose (`app/auth/keyed-hash.server.ts`); it is never stored. The estimate is read only after the token is proved, and a wrong token is the same 404 as an id that does not exist. The client accepts or declines once; staff may revert the decision.

Invoices and estimates are emailed only to the client's billing contacts, through the `EMAIL` binding, with the PDF attached, at most 200 sends per organisation a day; each send is recorded on the document's history. The scheduled handler (`workers/app.ts`, hourly cron in production only, none on previews) issues due recurring invoices and sends late reminders; running it twice in the same hour does the work once. CSV exports (the billing reports and the Xero file) prefix a cell a spreadsheet would read as a formula with `'`.

### The gate in front of the plugin

Every request to `/organization/*` passes one check of ours before the plugin sees it (`organisationRules` in `app/auth/organisations.server.ts`):

- **Only the endpoints we use exist.** The 15 listed in that file are answered; every other endpoint of the plugin gets 404, including the ones that set an "active organisation", check whether a slug is taken, look an organisation up by its slug or list the invitations sent to a person. An upgrade of Better Auth cannot add an endpoint unnoticed.
- **Input is exact.** Each endpoint has a strict Zod 4 schema. A missing field, a wrong type or a field that is not listed gets 400 and nothing is stored.
- **The organisation comes from the request.** Every endpoint that acts on an organisation must be given its id. The plugin records an "active organisation" on the session when a person creates or joins one; nothing reads it (`docs/decisions.md` entry 20).
- **"Not found" for anyone who is not a member.** The gate reads the person's membership through `organisationScope`. Without one the answer is `404 {"code":"ORGANIZATION_NOT_FOUND"}`, byte for byte the same whether the organisation does not exist or belongs to other people, and the plugin is not reached.

A signed-out request to one of the 15 gets 401 before its input is read.

### Creating an organisation

Any signed-in person whose email address is verified may create an organisation, and becomes its only member, as owner. A person may own at most 5 organisations; the next is refused with `403 {"code":"YOU_HAVE_REACHED_THE_MAXIMUM_NUMBER_OF_ORGANIZATIONS"}`. Organisations a person only belongs to are not counted, which is why the plugin's own `organizationLimit` is not used: it counts every membership. The request carries a name and nothing else. A name is 1 to 80 characters, with no line break, no other control character and none that reverses the direction of text, because it is shown in pages and quoted in the invitation email.

The slug is derived from the name on the server (`app/organisations/slug.ts`): lowercase letters, digits and hyphens, 3 to 40 characters, no hyphen at either end. It is never `new`, `settings`, `api`, `auth`, `app`, `admin`, `www`, `invitations`, `sign-in` or `sign-up`. When the slug is taken or reserved the organisation gets the next free number instead of an error: `acme`, `acme-2`, `acme-3`. Renaming an organisation does not change its slug, and no request can set one.

### Invitations

- An owner or admin invites an email address as `admin` or `member`. Ownership is never given by invitation.
- An address that is already a member, or already has a pending invitation to the same organisation, is refused. There is no "send again": that would extend the invitation's life.
- An invitation works for exactly 7 days and once. Accepting it needs a session whose verified email address is the invited one, compared without regard to capitals.
- An invitation that does not exist, has been accepted, declined or cancelled, has expired, or was sent to somebody else gets one answer, `404 {"code":"INVITATION_NOT_FOUND"}`, whether the request reads, accepts or declines it. The id tells nobody but its recipient anything.
- An invitation stands on its sender's right to invite. Once the person who sent it is no longer an owner or admin of that organisation, because they were removed, made a member or left, it can be neither read nor accepted and gets the same 404. It can still be declined. Otherwise an admin about to be removed could invite an address of their own and return with it.
- Cancelling names the organisation as well as the invitation, and only a pending invitation of that organisation can be cancelled.
- The email is sent with `sendEmail`, from the application's one sender, as plain text and plain HTML with no image or other remote content. Its subject is the same for every invitation, "You are invited to join an organisation on Timesifier", and holds nothing a person chose: the message goes to somebody who never asked for it. Its one link is `https://<host>/invitations/<id>`, where the host is the one the invitation was made on, which `app/auth/hosts.ts` has already checked is ours. The organisation's name appears in the body alone, quoted in the text and escaped in the HTML.
- The id in the link is a UUID version 7 with 74 random bits. It is not the only thing needed: the session of the invited address is.

### "Not found" for pages

Everything under `/app/<slug>/` sits below one layout, `app/routes/app/organisation.tsx`, whose `middleware` runs after the session guard and before the loader or action of every route under it, for a page and for a data request alike. It reads the person's membership of the organisation in the address from the database on that request, or throws React Router's 404. The 404 is the same for a slug no organisation has and for an organisation the person does not belong to, and the same two queries run in both cases. No route below repeats the check: each reads the organisation and the role from the layout's context and passes that organisation's id to the server, never an id from a form. `test/pages/isolation.test.ts` takes every route under the layout from the route configuration and requests each as a member of another organisation and for a slug that does not exist; a route added there is tested without anyone listing it.

An invitation's page, `/invitations/<id>`, is outside that layout. Signed out, it sends the person to sign in with `next` set to come back; `next` is honoured for a path under `/app` or exactly `/invitations/<id>`, and nothing else (`app/routes/auth/paths.ts`). Signed in as the invited address, it names the organisation and who sent the invitation. An invitation that is unknown, used, cancelled, expired, somebody else's, or whose sender may no longer invite gets one page with status 410 that does not say which (`test/pages/invitation.test.ts`).

A person's name is changed from Settings by a route action that validates it with the one rule for a name (`app/auth/person-name.ts`) and changes the name and nothing else; `/update-user` is not among the endpoints the mount answers.

### Organisations: abuse

Creating an organisation and sending an invitation each allow one client 10 requests a minute; the 11th gets 429. They are counted by the limiter described under "Authentication", and like it they apply only to requests that arrive at `/api/auth/`. Two caps are per person and not per client: 5 organisations owned (above), and 20 invitations sent in any 24 hours across all of a person's organisations, after which the answer is `429 {"code":"TOO_MANY_INVITATIONS"}` and nothing is stored or sent. An invitation is counted when it is made; cancelling it or deleting its organisation gives nothing back, and an invitation refused for another reason is not counted. The plugin's own ceilings are left at their defaults: 100 members and 100 pending invitations for an organisation.

### Organisations: what is stored

| Table           | Holds                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------- |
| `organisations` | Name and slug                                                                                  |
| `memberships`   | Which person belongs to which organisation, and their role                                     |
| `invitations`   | The invited address, the role offered, who sent it, when it expires and what became of it      |
| `sessions`      | One more column, the plugin's "active organisation", which the plugin writes and nothing reads |

Deleting an organisation deletes its row, and every table of the organisation goes with it: each has a foreign key to `organisations` that cascades (`test/claims.test.ts` holds it), and its receipts in R2 are deleted first (see "Receipts"). A person's account is not deleted with an organisation. An invitation works for seven days; its row stays afterwards, with what became of it, until the organisation is deleted.

### Organisations: never logged

No log line carries an email address or an invitation's id. `test/organisations/invitations.test.ts` reads every line logged while an invitation is sent, accepted and refused, and fails if one appears.

## Browser policy

Set by the Worker in `workers/app.ts` on every response it produces. The tests in `test/browser-policy.test.ts` hold it in place.

### One host in production

Production answers only on the host its deployment names in `APP_HOST`, which for this project is `timesifier.com`. `www.` in front of it is redirected to it with status 308, and any other host gets 404 (`workers/canonical-host.ts`).

The reason is a Cloudflare behaviour: with `preview_urls` on, which pull-request previews need, every uploaded version of the Worker also gets its own address, `<version>-<worker>.<account>.workers.dev`, bound to the production database. Without the host check an old version with a fixed bug would stay reachable there for good. The smoke test after each deploy asks the new version's address for the home page and fails unless it gets 404.

The Worker knows it is production from the variable `ENVIRONMENT`, which the pipeline writes; a missing or unknown value counts as production. A production Worker whose `APP_HOST` is missing, or is not exactly a host name, has no host of its own: it answers 500 on every host and redirects nowhere. Previews set `ENVIRONMENT` to `preview` and answer on their own addresses. A loopback host (`localhost`, `127.0.0.1`) is always served, which is what local development and the browser tests use; Cloudflare never routes such a host to the Worker.

Plain HTTP is redirected to HTTPS by the zone's "Always Use HTTPS" setting, which is on. The smoke test checks it.

### Headers

Every response from the Worker carries:

| Header                      | Value              |
| --------------------------- | ------------------ |
| `Strict-Transport-Security` | `max-age=63072000` |
| `X-Content-Type-Options`    | `nosniff`          |

A response that is not HTML (a redirect, a refusal, data) also carries `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, so a response opened on its own can load and run nothing.

A response whose content type is HTML, including error pages, also carries:

| Header                       | Value                                                                                                                                               |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Content-Security-Policy`    | See below                                                                                                                                           |
| `Referrer-Policy`            | `strict-origin-when-cross-origin`                                                                                                                   |
| `X-Frame-Options`            | `DENY`                                                                                                                                              |
| `Cross-Origin-Opener-Policy` | `same-origin`                                                                                                                                       |
| `Permissions-Policy`         | Every feature in the list in `workers/security-headers.ts` is denied with `=()`, the two for public-key credentials among them. Nothing is allowed. |

Files in `public/` and the built scripts and styles are served by Workers Static Assets before the Worker runs, so the Worker cannot add headers to them. `public/_headers` gives them `X-Content-Type-Options: nosniff`, the same HSTS value and the same "nothing loads" policy. That policy matters when a file is opened directly; it does not affect a page that loads the file. The files under `/assets/`, every one named by Vite with a hash of its content, are also `Cache-Control: public, max-age=31536000, immutable`: they hold no customer data, and a file at one address never changes. Everything else in `public/` keeps the platform's `max-age=0, must-revalidate`, and pages and their `.data` answers stay `private, no-store`.

**HSTS has no `includeSubDomains` and no `preload`.** Other subdomains of `timesifier.com` belong to other services (see `docs/architecture.md`). `includeSubDomains` would make browsers refuse plain HTTP on every one of them, and `preload` requires it and is slow to undo. Without it the header applies only to the host that sent it.

### Content Security Policy

```
default-src 'self';
script-src 'self' 'nonce-<random>';
style-src 'self' 'sha256-<usePress>' 'sha256-<usePreventScroll>';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
base-uri 'none';
form-action 'self';
frame-ancestors 'none';
object-src 'none'
```

- The nonce is 128 random bits from Web Crypto, new for every request. The Worker creates it, passes it to `app/entry.server.tsx` through the router context, and writes the header. `ServerRouter` and React put it on every inline script they emit.
- There is no `unsafe-inline`, no `unsafe-eval` and no `strict-dynamic`. Scripts are our own files, allowed by `'self'`; only the inline scripts need the nonce.
- **`style-src` allows our own stylesheets and two `<style>` elements by hash, nothing else.** A `style` attribute, and any other `<style>` element, is ignored by the browser, so the page looks wrong without failing. React's `style` prop becomes a `style` attribute in the server-rendered HTML, so it is blocked on first paint. Style with classes and design tokens. A value that must be computed at run time is set from script after hydration through the CSSOM (`element.style.setProperty(…)`), which the policy allows. Check what a library renders on the server before adding it.
- Add a new source only with the card that needs it, and record it here. One has been added, for one page only: see "Turnstile on the page".

### The two hashes

React Aria (TS-005) inserts two `<style>` elements from script. Each has a fixed text, so each is allowed by the SHA-256 hash of that text. A hash allows one exact text: it lets in no other inline style, and no `style` attribute.

| Hash                                                  | Inserted by                                                    | Text                                                                               | What it does                                                                                                                   |
| ----------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `sha256-38RhXrc7EdReTKsOm23ZPOCUgniTUUcjky8QOOrQx6o=` | `usePress`, once, when the first pressable element mounts      | `@layer { [data-react-aria-pressable] { touch-action: pan-x pan-y pinch-zoom; } }` | Stops the browser waiting for a double tap before it reports a press.                                                          |
| `sha256-gYiS/BvZvRcK27JIXTuwhZ3hs2+VJ1X+2gUlE+farlg=` | `usePreventScroll`, on iOS only, while a modal overlay is open | `@layer { * { overscroll-behavior: contain; } }`                                   | Keeps the page from scrolling behind an open dialog, sheet, select or menu. Other browsers get `overflow: hidden` on the page. |

The table shows each text on one line; the hashed text has the line breaks the library writes.

- The list is `REACT_ARIA_STYLE_HASHES` in `workers/security-headers.ts`.
- **Re-derive it on every React Aria upgrade.** `test/node/react-aria-styles.test.ts` reads the installed `react-aria`, `react-aria-components` and `react-stately`, finds every module that creates a `<style>` element, takes each text and hashes it. It fails when the library inserts a text the policy does not allow, when the policy allows a text the library no longer inserts, or when a new module starts creating `<style>` elements, and its message gives the hash to use. Update the list, `test/browser-policy.test.ts` and this table together.
- The browser tests are the second check: every one fails on a `securitypolicyviolation` event, in Chromium and, for the overlays, in WebKit on the iOS path (`e2e/fixtures.ts`, `e2e/overlays-ios.spec.ts`). `e2e/react-aria-style.spec.ts` runs in WebKit alone, at a desktop's size and on an iPhone, and checks that the pressable `<style>` is applied (its sheet has its one rule, and a pressable element's `touch-action` is the rule's) on the gallery and the sign-in page.
- **Why not React Aria's nonce.** The installed React Aria can also stamp its `<style>` elements with a nonce it reads from `<meta property="csp-nonce">` (`getNonce` in `react-aria/dist/private/utils`). That is not used: a nonce on the page allows any `<style>` a script inserts with it, where a hash allows one exact text.
- **A WebKit console that shows "Refused to apply a stylesheet because its hash, its nonce, or 'unsafe-inline' does not appear in the style-src directive" after a Playwright screenshot is Playwright's, not ours.** In WebKit, `page.screenshot()` inserts a `<style>` of its own into the page (its text is `body {}`), and the policy blocks it as it should. Measured on 2026-11-11 with Playwright's WebKit at an iPhone's size: on the production site's `/sign-in` and `/privacy`, and on `/design` in a local build, there is no violation while the page loads and is used, React Aria's pressable `<style>` is applied, and there is one violation, `style-src-elem`, right after each screenshot. That was audit W19's report; nothing in the policy changed for it. A browser test that wants a screenshot takes it after its checks of the policy, or leaves the policy out of what it claims.

### What components do to live under the policy

- **No `style` attribute reaches the server-rendered HTML.** React Aria's Checkbox, Switch and Select components hide a native input or select with a `style` attribute. Ours are built on React Aria's hooks instead and hide that element with a class (`app/components/Checkbox.tsx`, `Switch.tsx`, `Select.tsx`). The reasoning and the measurements are in `docs/decisions.md`, entry 6.
- **Overlays are positioned from script.** A menu, a select list, a tooltip, a dialog and a sheet render only in the browser, after hydration, and React sets their position through the CSSOM. They are never in the server's HTML.
- **Before using another React Aria component, render it with `renderToString` and look for `style=`.** The date and time components carry `style` attributes and will need the hooks.

### Relaxed under `pnpm dev`

Only when `import.meta.env.DEV` is true:

- `style-src` is `'self' 'unsafe-inline'`, without the two hashes. The Vite dev server injects stylesheets as `<style>` elements so it can hot-reload them, and a browser ignores `'unsafe-inline'` in a directive that also carries a hash.

Nothing else changes. The hot-reload WebSocket is same-origin and allowed by `connect-src 'self'`. Tests run with `DEV` false and check the policy that ships; the browser tests run against a production build for the same reason.

### Origin check

Before the framework sees a request, the Worker answers 403 to a `POST`, `PUT`, `PATCH` or `DELETE`, and to a WebSocket handshake (a `GET` with `Upgrade: websocket`), when:

- `Origin` is present and is not the origin of the request's own URL, or
- `Sec-Fetch-Site` is present and is neither `same-origin` nor `none`.

A request with neither header is let through: browsers send `Origin` on these methods, so it is not from a browser and cannot carry a person's session by forgery. Session cookies are `SameSite=Lax` as a second layer. `GET`, `HEAD` and `OPTIONS` are never blocked, so they must never change state.

React Router has its own check: it answers 400 to a page or data request with a state-changing method whose `Origin` is not the request's host. It does not cover resource routes. The Worker's check covers every route.

### Input validation

Every action begins with `parseRequest(request, schema)` from `app/lib/validate.ts`. It reads form data or JSON, checks it against a Zod 4 schema and returns the typed result. When the body cannot be read or does not match, it throws a 400 response whose body is `{ errors: { form: string[], fields: Record<string, string[]> } }`. The response holds messages and field names, never the submitted values; a custom message in a schema must not include the input either.

A body larger than 64 KiB is answered 413 and is not read past the limit; an action that accepts a file passes a larger `maxBytes`. A form field named `__proto__` is an ordinary field: it cannot change the parsed object's prototype.

`test/action-validation.test.ts` finds every route that exports an `action` and fails until that route has a malformed request listed there that receives 400.

### The colour-scheme cookie

`__Host-color-scheme` holds the word `light`, `dark` or `system`, the choice a person made in Settings, with `Secure`, `SameSite=Lax`, `Path=/`, no `Domain` and a life of one year; it is not `HttpOnly` because it identifies nobody and grants nothing, so there is nothing for a script to steal. It is not set until a person chooses. The server writes it only from the validated Settings form and reads from it only one of those three words: no cookie, or any other value, is `light` (`app/shell/color-scheme.server.ts`, `test/color-scheme.test.ts`).

### The getting-started cookie

`__Host-timesifier.getting_started` keeps two marks of the Timesheet's getting started (TS-056): that a person has opened the Week view, and that they put the list away. Each mark is a letter and the person's user id, newest first, at most ten, so that two people who sign in on one browser keep their own; there is no database column for either, and adding one would need a migration for a hint. It has `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain` and a life of one year. It grants nothing: a forged mark ticks a step or hides the list for whoever forged it. The server writes it only from the Timesheet's loader, when the Week view is opened, and from its `put-away` action, and reads from it only marks of the person signed in; anything that is not a mark is dropped (`app/timesheet/getting-started.server.ts`, `test/pages/timesheet.test.ts`).

### Turnstile on the page

Turnstile loads a script from Cloudflare and runs in a frame. One page shows the widget, `/sign-in`, and only its policy has the two sources it needs:

```
script-src 'self' 'nonce-<random>' https://challenges.cloudflare.com;
frame-src https://challenges.cloudflare.com;
```

Every other directive on that page, and the whole policy of every other page, is the one above.

- **How a page gets the addition.** The route exports `headers` and sets `Timesifier-Policy-Addition: turnstile` on its own response. `withSecurityHeaders` in `workers/security-headers.ts` reads the header, removes it, and builds the policy with the addition. The header never reaches a browser, a request cannot set it, a value other than `turnstile` adds nothing, and a response that is not HTML gets the "nothing loads" policy whatever it names. A page that does not ask keeps the base policy. To give another page the widget, export the same `headers` from its route and add the route to the tests named below.
- **Why the host is listed.** The nonce is on the `<script>` element that loads `https://challenges.cloudflare.com/turnstile/v0/api.js`, and the policy has no `strict-dynamic`, so the scripts Turnstile then loads for itself need the host. Without `frame-src`, a frame falls back to `default-src 'self'`.
- **Moving between pages loads the page.** A document keeps the policy it was loaded with, so the page with the addition and the pages without it are never reached from one another by a move inside the page: the links between them are plain links (the public pages' band and foot, which the sign-in page shares, are plain HTML), the guard redirects with `redirectDocument`, and the pages leave with `location.assign`. `e2e/one-way-in.spec.ts`, "every way to the sign-in page is a whole page load", arrives by each of them and then sends a code.
- **Where the widget runs.** `app/routes/auth/RobotCheck.tsx` renders it explicitly, on the views that send a code and nowhere else: the first view of `/sign-in`, and the view that takes the code, which can send another. The site key comes from `TURNSTILE_SITE_KEY` through the route's loader. The token goes to the server in the `x-captcha-response` header; the widget is told to add no form field.
- **The mode.** The production widget is set to Cloudflare's non-interactive mode: it never shows a tick box.
- **When the check fails.** The page says "We could not confirm this browser. Wait a moment and press Continue again." and pressing the button again runs the check again: the widget is reset, or its script is fetched again if it never arrived. Nothing is sent to the server without a token.
- **What the widget does to our document.** Measured in Chromium on 2026-11-11: it adds one `div` to the element it is given, with a closed shadow root that holds its frame, and sizes the frame through the CSSOM, which the policy allows. It adds no `<style>` element and no `style` attribute to our markup, and raises no violation. `e2e/auth-turnstile.spec.ts` holds this in place, and the fixture every browser test shares fails any test on a violation.

Checked on 2026-11-11 against <https://developers.cloudflare.com/turnstile/reference/content-security-policy/>. `connect-src 'self'` is already enough for pre-clearance mode. Tests: `test/browser-policy.test.ts`, "the Turnstile addition to the policy"; `e2e/auth-turnstile.spec.ts`. The token is verified on the server by Better Auth before a code is created; see "Authentication" above.

## Secrets

Secrets are stored once, in a place built for them, and read directly from there. Nothing that belongs to one deployment is in the repository either: no domain, no database id, no key, no address. The code and the pipeline read each from a setting, and this section is the one list of them.

| Where the code runs             | Where a secret lives                                                                        | Where a variable lives                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Local development and the tests | `.dev.vars` in the project folder, ignored by git, readable only by the owner (`chmod 600`) | `vars` in the committed `wrangler.jsonc`, with values that reach nothing        |
| Deployed Worker                 | Wrangler secrets                                                                            | The Worker's variables, which the pipeline writes from the repository variables |
| Pipeline                        | GitHub Actions secrets                                                                      | GitHub Actions repository variables                                             |
| Wrangler on the owner's machine | Wrangler's own login                                                                        |                                                                                 |

No command fetches a secret from a password manager each time it runs. A new secret or variable is added to all the places it is needed in the same change, to the table below, and to `scripts/deploy-config.ts` if the pipeline needs it; a secret's name (never its value) is listed in `.dev.vars.example`.

### How a deployment gets its values

The committed `wrangler.jsonc` is a developer's machine's: `ENVIRONMENT` is `development`, the Turnstile site key is Cloudflare's published test key, both database ids are `00000000-0000-0000-0000-000000000000`, and there is no route and no allowed sender. A command run from a clone therefore reaches no production resource, even with `--remote` and the owner's login: Wrangler uses an id it is given and never looks a database up by name, and that id is no database's.

In the pipeline, before anything is built, `node scripts/deploy-config.ts --write` reads the six repository variables, checks that each is set and is what it must be, and that the two Cloudflare secrets are set. If not, the job fails there with one line for each, by name. Otherwise it rewrites `wrangler.jsonc` in the job's checkout with the deployment's values and writes `wrangler.preview-migrations.jsonc`, which is not in the repository. The build then copies that configuration into its output, which is what `wrangler deploy` and `wrangler preview` upload. Wrangler 4.159 has no way to read a value of its configuration from the environment (its environment variables are about Wrangler itself: <https://developers.cloudflare.com/workers/wrangler/system-environment-variables/>), `wrangler d1 migrations apply` reads `wrangler.jsonc` itself, and the Cloudflare Vite plugin's own `config` option reaches the build but not that command; so the file is what is rewritten, by one script. `scripts/deploy-config.test.ts` holds the check, the rewrite and the committed file's emptiness in place.

## Rules for anyone changing the code, human or AI

- Keep secret values out of code, logs, commit messages, pull requests and chat.
- Production data changes go through migrations in the pipeline.
- The privacy notice (`app/routes/privacy.tsx`) says what is stored, which cookies are set, who handles the data and for how long. A change to any of those changes the notice in the same pull request; `test/documents.test.ts` fails when a cookie's name is not on it.
- DNS changes on `timesifier.com` are limited to the Worker's custom domains and the application's one email subdomain. The zone carries live email for other services; see `docs/architecture.md`.
- A new dependency needs a reason in the pull request: what it does, who maintains it, why the platform or an existing dependency cannot do it.
- Report a suspected vulnerability to the owner privately before opening an issue.
- A Better Auth upgrade is a card of its own. Its pull request changes nothing else, and `test/auth/endpoints.test.ts` shows which endpoints the new version registers.
